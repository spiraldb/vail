# Prefix scan with native Int32 widening — 2026-10-13

The optimized release now uses the native DataFusion window/partition-summary path for the exact benchmark workload, `range_table(1_000_000, n_partitions=14).annotate(prefix=scan.sum(idx))`. Its physical plan has local bounded windows, partitioned native `sum(idx)` partial/final aggregates and a carry window; it contains no `vail_scan_state`. The result type is Int64. The plan and binary hash are saved in `physical-plan.txt`.

The matched Vail run passed all checks (Python 3.11.13, arm64, 14 cores, 1M rows, 14 partitions, 3 warmups, 5 measured iterations). It took 0.200520, 0.201827, 0.209525, 0.206053, and 0.197646 seconds; median 0.201827 seconds. This is 7.4% faster than the recorded Hail median of 0.2179 seconds, and 71.4% faster than the earlier Vail generic-path median of 0.704604 seconds. The latter comparison identifies the gain from actually selecting the fast path; it is not a comparison of two optimized builds.

The optimized Samply run completed successfully at 500 Hz with the independent 10 Hz telemetry collector. Its median was 0.202707 seconds (3 warmups, 5 iterations), mean 1.53 cores, peak 361.5 MiB RSS, and peak 119.0 MiB physical footprint. Ten 100 ms telemetry samples overlapped measured iterations. Median rates were 33.28 billion instructions/s and 5.57 billion cycles/s, IPC 5.96. The host API does not expose cache-miss counters. The native profile, symbol sidecar, measured-only hotspots, folded stacks, SVG flamegraph, raw metrics and iteration data are in `profiled/`; PNG/telemetry rendering is unavailable because Matplotlib is absent from this benchmark environment.

The profile no longer shows `HailAccumulator`, `StateAccumulator`, or `ScalarValue::iter_to_array` as the main path. Its largest leaf samples are allocator/free-list work (7.7% `free_tiny`, 5.5% `tiny_malloc_from_free_list`, 3.5% `tiny_malloc_should_clear`) followed by DataFusion's sorted-stream merge loser tree (4.1%), with additional Arrow row comparison and window evaluation. This suggests remaining cost is in native window sorting/merge and allocation rather than per-row aggregate-state materialization. No further optimization is claimed from this profile.
