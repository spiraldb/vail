# Paired legacy-file reads

Both engines read the same files written by Hail. All six action results matched. Two warmups, five measured runs; medians include opening and execution, exclude startup. Sequential engines, warm local cache, shared 14-core Apple M3 Max laptop.

| Action | Hail seconds | Vail seconds | Result |
|---|---:|---:|---|
| table_force_count | 0.1710 | 0.0508 | Vail 3.36× faster |
| table_scalar_sum | 0.1568 | 0.0500 | Vail 3.14× faster |
| matrix_decode_count | 0.4063 | 2.0898 | Hail 5.14× faster |
| matrix_decode_count_gt | 0.3426 | 1.9703 | Hail 5.75× faster |
| matrix_entries_count | 1.2812 | 5.2877 | Hail 4.13× faster |
| matrix_sum_dp | 0.3777 | 2.0209 | Hail 5.35× faster |

Table: synthetic 1M rows / 16 partitions, generated by Hail with `legacy_read.py`. Matrix: actual upstream profile25 VCF fixture written by Hail 0.2.139, 24,885 rows × 2,535 columns, 16 partitions. Matrix decode/count, GT projection and entries-count actions match upstream `benchmark_matrix_table.py`; DP sum additionally verifies values.

Vail wins these table cases but loses all measured matrix cases. The current matrix source uses `matrix_stream` rather than the table Vortex layout path and decodes complete selected entry structs; GT-only and DP-only operations cannot prune nested entry fields. This is a concrete implementation limitation, not evidence that legacy matrix performance meets the Hail target. Profiling is needed to assign the remaining cost.

This is a targeted comparison, not the complete upstream suite. The published many-int/string inputs require ~1.06 GB compressed plus output storage; this run had only ~2.2 GiB free. No distributed or cold-cache claims. Hail ran on Java 21 with its Java 11 compatibility warning.
