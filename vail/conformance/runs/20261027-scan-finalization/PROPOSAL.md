## Existing library-level reuse direction

Explore a **prepared state-finalizer strategy** selected from aggregate identity/type/options once, with an existing native DataFusion GroupsAccumulator as the first candidate for aggregates that support it. Map each visible snapshot to a distinct output group, merge the whole state batch once, and evaluate native groups once. This could remove per-output factories/slices/ScalarValues while retaining native AVG/stddev/corr numerical math/state conventions, rather than copying a scalar algorithm or inventing SIMD. The existing aggregate's group-state contract must actually match scalar state fields and return metadata. Do not assume groups-supported implies scalar-state compatibility for arbitrary custom/indexed reducers.

Native group merge lacks a filter argument. Null outer states denote empty frames, NOT permission to merge arbitrary hidden child payload. Admit only a proved state representation with null-ancestor handling: visible state rows selected/borrowed before merge, explicit group-index mapping and no envelope copies of excluded gaps; absent groups must produce the same empty normalization as scalar evaluation. All-null/zero-row states and defined empty states differ. Existing normalize_empty_collect and Hail mean-emptyNaN behavior remain. Nested/opaque/unsupported state layouts keep the old route until explicit proof, no recursive compactor.

Prepare immutable descriptors/group factory selection at query construction. Actual accumulator state must be worker-local and reset using a documented native lifecycle (e.g. complete EmitTo::All), with no shared global cache or per-output factory. If the API only safely permits per-batch instance creation, disclose that boundary and obtain performance/design review rather than claiming once-per-query execution. Mutable owner lifetime/concurrency and retained capacity accounting must be explicit before any implementation; one accumulator per snapshot is precisely what this proposal aims to remove. Group indices can use a reusable batch buffer, not repeated hash/name lookups. This is a possible native-library adapter, not a claim that a drop-in supported API already solves every scan.
