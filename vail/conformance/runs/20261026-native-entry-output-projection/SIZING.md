# H051 sizing checkpoint: safe scalar fallback, not performance-clear

No runtime narrowing is wired. Original source ID and complete `batch_memory_size` are captured before any view and remain the EXACT KeyRun and singleton charging inputs. The following sidecar concerns only output batch row limits; it cannot alter64MiB spill decisions or8192singleton caps.

A scalar upper bound needing no new nested traversal is `owner_charge = saturating_add(original_row.get_array_memory_size(), original_entry_values.get_array_memory_size())`, captured by the existing original binding before views, plus original column Struct full get_array_memory_size captured once before its view. Units are bytes per ONE output record: deliberately no average/length division. For slices carry the unchanged charge; for singleton concat use saturating sum across contributing fragments (or source-ID dedup only when identity is proven); KeyRun spills retain the scalar in a parallel batch-index sidecar, restored with exactly that batch on reload. No array owner is retained for sizing. Empty input emits nothing; zero charge becomes1; overflow or unrepresentable charge forces limit1. The output row cap is `min(8192, max(1, 32MiB / charge))`. This cannot produce a larger chunk than the old original-owner heuristic because each of its row/entry/column divided terms is no larger than its corresponding whole-owner charge; concat sum is a conservative scalar owner bound, not an allocator byte-bound claim.

This is a correctness-safe fallback but likely unacceptable performance: wide entry owners exceed32MiB, so it can force one-record output. It must not be silently shipped as a performance improvement. A tighter average rule from original source rows/entries is cheaper but NOT automatically conservative under variable-width selected-row skew; it is not proposed as proven. Tight equivalence would require new recursive payload accounting or retention/copy of unused owners, both outside the approved scope. The next decision is whether to measure this explicitly pessimistic scalar policy, or deliberately relax exact conservatism of the pre-existing32MiB heuristic while retaining its constants and original per-unit estimates. No claim is made that these alternatives are equivalent.
