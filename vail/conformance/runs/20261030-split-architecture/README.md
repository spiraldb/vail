# Split HTS execution investigation — 2026-10-30

Default split evaluates the entry-preparation prefix twice on both tested fixtures. On the public 200-row × 2,535-sample subset, diagnostic UDF batch counters record 1,014,000 entry preparations versus 507,000 with `permit_shuffle=True`; both produce 204 rows. Logical subplan memoization does not establish evaluated-producer ownership across the two ordered-union branches. These are exact observations for the pinned diagnostic binary/actions, not a universal twofold total-CPU claim.

The local profile also exposes four list-dispatch calls and up to four Arrow child-array constructions per original entry (for defined input lists) and newly allocated PL workspace per entry. Candidate `bf9d8aed5` prepares borrowed primitive list views once per batch and reuses workspace. It changes no numerical reduction, branch/filter policy, output order, or error domain. The entry-only prototype showed real-subset process-median ratios of 0.917 wall and 0.770 process CPU, with generated default action-wall ratio 1.003 retained. These shared-host diagnostic timings do not establish full benchmark speedup or superiority over Hail. See ANALYSIS.json for all modes and rejected iterations.

Simply filtering branches earlier is not admitted: 24 of 40 public action observations switch from existing errors to zero-output success. A proper shared evaluated-producer boundary must precede separate branch lowering and preserve the original domain. Replay memory, IPC, lag, repeated/concurrent actions and cancellation need review; an eager cache or structural expression CSE is not a substitute.

Normal-build receipts, complete-result comparisons, public test logs, scripts, source snapshots, counters and raw timing/profile records are retained in the accompanying archive. Large VCF/MatrixTable inputs and compiled wheels are not checked in; their identities are recorded. Final uninstrumented candidate gates: 3 Rust tests and 30 public split tests passed, and all complete-result oracles matched. Independent source/correctness review cleared exact revision bf9d8aed5.

The first real candidate process wall median was above the faster baseline process for both modes; these are short shared-host diagnostics, not a universal-win claim. All earlier adverse/negative observations remain in ANALYSIS.json and the raw archive.

A separate one-row fixture with BOTH an unchanged and a moved alternate produces equal complete results but records eight entry preparations for four input entries in both baseline and early-filter variants. Moving filters alone therefore does not generally eliminate duplicate all-alt reductions. It also changes the public error domain as noted above.

There is a second independent architectural limitation: OrderedUnion currently produces one output partition through SortPreservingMergeExec. Moving all final entry work after it can serialize that work (the local placement experiment was adverse). Sharing a producer addresses duplicate execution, not this partition collapse. A general range-aware rekey/ordered union would need normalized-key bounds and explicit tie/order guarantees. Hail source applies entry annotation after split_multi, but no Hail execution/kernel counts were measured in this investigation.
