## Public route and remaining invariant decisions

`m.annotate_rows(sampled=hl.agg.take(m.DP,8))` is an actual entry-list pipeline. `agg_collections.py:take` requires a Python nonnegative int and packs n into aggregate options. `matrix_list_aggregates.py:reduce_list` maps the entry expression, emits n as literal Int64 and selects either __vail_list_reduce_take or __vail_list_reduce_take_ordered. The distinction and n are fixed when the query is constructed. Global/grouped take uses a separate configured aggregate route and is not the proposed first scope.

`list_aggregate.rs:ListAggregate::invoke_with_args` still expands scalar initializers to an Arrow array per batch. The generic row loop branches on initializer presence, matches Int32/Int64, validates missing/negative n, tests previous n, and chooses configured aggregate factory. Previous-kernel caching only spans consecutive rows within that invocation: it does not prepare the known literal n once query. Each defined row creates an accumulator, a list value header, invokes update/evaluate, and finally rebuilds all row ScalarValues with iter_to_array. Some residual direct-call/dynamic-initializer contracts are broader than the Python API; those must retain explicit fallback rather than silently assuming every caller uses a literal.

For unordered take, `advanced_collection_aggregates.rs:TakeAccumulator::append` allocates a UInt32 prefix index vector and calls Arrow take on each row, stores one owned chunk, then creates a ScalarValue List; final list aggregation reconstructs these outputs again. These are source-confirmed per-row setup/copies. For ordered take, it uses Arrow lexsort_to_indices with Some(n), followed by Arrow take; Arrow already uses a partial-sort limit, so do not label this as a proven full-sort bug. Empty/defined/missing list distinctions, field/opaque metadata, stable tie/error/float ordering and bounded retained ownership need independent public oracles before expansion.

## Library reuse trap: array_slice capacity

DataFusion55 extract.rs:general_array_slice does coalesced Arrow MutableArrayData selection and skips null parents, but initializes Capacities::Array(original_data.len()) before determining selected prefixes. Rewriting take(8) over very wide lists directly to this function can reserve full input-child capacity even when output is only eight values per row. It also plans from/to/stride per row despite known prefix configuration. This is a source resource risk, not a measured regression. A generic DF capacity improvement may be worthwhile separately, but a new fork of the entire nested-functions crate is a maintenance cost; do not assume the builtin solves this task without a capacity gate.

A prepared prefix-list adapter could choose n/type once query, borrow only when the whole visible list payload is retained with a valid owner envelope, otherwise use one final offset vector and coalesced Arrow MutableArrayData ranges sized to sum(min(n,defined_row_width)). No per-row accumulator, index vector, ScalarValue/header or function/type dispatch is needed. This would reuse Arrow's existing range-copy machinery, not invent arithmetic/SIMD. However it is an opaque scalar node unless expressed through a safe standard DF operator; optimizer transparency and future Vortex list-prefix projection support should be considered before choosing. No implementation decision yet.
