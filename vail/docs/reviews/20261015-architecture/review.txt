VAIL ARCHITECTURAL REVIEW — 2026-10-15
Reviewed source: 6a61cf9 (before this report). File fingerprints: inventory.json.

VERDICT

Vail has useful foundations, but it is not yet one coherent compiler. Much of
its complexity comes from preserving Hail's observable order, partition identity,
missingness, and randomness through a SQL engine that does not express all of
those properties. Those differences are real. The problem is that Vail handles
them in several places using physical wrappers, incidental Arrow fields, string
markers, and separate expression rewrites. A feature can be locally correct
while its composition with another feature is wrong or disproportionately costly.

The most urgent issue is not the number of missing APIs. It is that an operation's
physical partition layout, TableIR metadata, and random identity can disagree.
This review found and reproduced precisely that disagreement with only 12 rows.

This is an architectural source review, not a claim of exhaustive verification.
I read the central implementations and followed their interactions, inspected
interfaces and selected implementation paths in the remaining modules, and
recorded each production module below. I did not read every line of every module,
rerun the full suite, or audit all third-party dependencies. The inventory makes
the boundary explicit: 47 Python frontend modules, 65 Rust source modules, and
support tooling. Tests/examples/data and historical reports are supporting evidence,
not individually reviewed production modules. Upstream Hail, DataFusion, Iceberg,
and Vortex checkouts are dependency sources, not Vail-owned modules; the integration
and patch boundaries are reviewed below. This is not a security audit.

Evidence levels used below:
  CONFIRMED: reproduced behavior or a direct, unavoidable code-path property.
  DESIGN: a boundary or representation that predictably creates maintenance,
          latency, throughput, or semantic risk; not an assertion of a new bug.
  INVESTIGATE: a plausible failure that this review has not demonstrated.
A module with no newly isolated defect is not thereby certified correct.

PRIORITY FINDINGS

1. HIGH / CONFIRMED: random annotation changes logical partition membership.
   Source: crates/vail-table/src/logical.rs, lower_rng_uids, especially
   child.known_n_partitions().unwrap_or(1) at the restore_partitions call.
   The restored physical range has one partition whenever the static count is
   unknown. TableIR's n_partitions still derives the actual interval count.

   Reproduction (reproduce_rng_partition_loss.py, captured log alongside it):
     write range_table(12, n_partitions=4), read it, filter idx < 8.
     Before annotation: n_partitions=3, count=8, partition 0 has 3 rows.
     After annotate(random_value=rand_unif(seed=7)):
       n_partitions=3, count=8, partition 0 has 8 rows.
   The earlier 346-row fixture similarly reports 15 partitions, with partition
   zero changing from 18 rows to all 245 rows after random annotation.
   No changed upstream assertion is needed to expose this bug. Adding a scalar
   field must preserve partition membership. The diagnostic script intentionally
   exits with AssertionError on the reviewed native build.

   Design consequence: UNKNOWN IS NOT ONE. Partition identity needs an explicit
   logical property/descriptor retained through numbering and lowering. Resolving
   a metadata count asynchronously, retaining a symbolic layout, or restoring
   from the actual planned input are possible implementations; silently inventing
   one partition is not. Audit scan restoration for the same assumption.

2. HIGH / DESIGN: there are still two relational compilers and runtime bridges.
   Sources: table/logical.rs, plan.rs, partitioned.rs, deferred_logical.rs,
   initialized_aggregate.rs, initialized_scan.rs, lookup.rs, joins.rs, zip_join.rs.
   Ordinary nodes lower logically, while special nodes invoke prepare_legacy and
   construct physical joins/windows/projections directly. DeferredLogicalExec
   creates a physical plan during execute(); DeferredOrderedExec prepares a
   TableIR during execute(). Schemas and explain output cannot fully expose the
   eventual work, and optimizer/resource decisions cross separately planned trees.
   These bridges are understandable migration devices, not a desirable endpoint.
   Keep logical extension nodes for genuine Hail semantics, but have their
   implementation consume already-planned child inputs. Retire the general
   physical TableIR compiler operator by operator. Merely moving a physical
   subtree behind a logical extension does not complete this migration.

3. HIGH / CONFIRMED ALGORITHM: stream aggregate-scan recomputes every prefix.
   Source: python/vail/streams.py, StreamExpression._aggregate_scan.
   It builds prefix = array[:position], then aggregate(prefix, ...) inside a map
   over every position. Even count/sum prefixes perform total work proportional
   to 0+1+...+(n-1), rather than maintaining accumulator state. Arbitrary callback
   scans can require sequential work; repeating all previous input is avoidable.
   Give streams a real scan/fold operation using reducer state. Do not advertise
   this fallback as the same scalable scan abstraction as Table scans. There is
   no new wall-clock benchmark in this review; the quadratic algorithm is visible
   directly in the construction.

4. HIGH / DESIGN: aggregate semantics are independently implemented by domain.
   Sources: Python array_aggregate.py and matrix_list_aggregates.py; Rust
   logical_aggregation.rs, logical_nested_aggregation.rs, aggregates.rs,
   advanced_*_aggregates.rs, scan_state.rs and scan_scopes.rs.
   Matrix row call_stats builds per-allele maps over the calls; table call_stats
   uses a native accumulator. Matrix mean/stddev build list arithmetic; table
   statistics have separate accumulator state and empty-result conventions.
   This is more than choosing a physical strategy: it duplicates the algorithm,
   null behavior, validation, numerical stability, and supported reducer list.
   The matrix call_stats path scans calls per allele (O(calls * alleles)); the
   native counts implementation has a more appropriate state representation.
   Use one reducer specification (argument types, initializer scope, state,
   update/merge/finalize, empty identity, ordering requirement) and adapt it to
   relations, row-owned lists, array coordinates, and scans. array_aggregate.rs's
   coordinate UDAF is a good example of this direction; do not replace every
   efficient list operation with relational unnesting.

5. HIGH / DESIGN: opaque volatile UDFs are the default escape hatch for pure work.
   Source: execution/logical_expr.rs, logical_kernel and restore_type.
   A kernel is compiled from a captured physical expression, gets a fresh name
   from NEXT_KERNEL_ID, and is declared Volatile. Referenced columns are correctly
   explicit arguments (keep this). But equivalent pure kernels have different
   optimizer identities; constant folding and expression reuse are inhibited.
   restore_type is also volatile to defend metadata. This uses semantic volatility
   to compensate for representation/optimizer issues. Introduce stable structural
   kernel identities and accurate effect classification. Metadata restoration
   should be a typed boundary, not a reason to mark ordinary arithmetic volatile.
   Do not simply flip these to Immutable: the existing metadata and random-context
   invariants must first be made explicit.

6. HIGH / CONFIRMED ALGORITHM: VCF export materializes the whole matrix in Python.
   Source: python/vail/vcf_export.py, samples=cols().collect() and
   localize_entries(...).collect() before opening output.
   Collecting sample IDs is reasonable for a VCF header. Collecting every row and
   entry before writing is not: peak memory scales with the complete matrix and
   Python object expansion, and time-to-first-output waits for the whole action.
   Basic serialization is useful as a fixture implementation, but should not be
   presented as a general dataset sink. Stream native batches into a bounded
   writer; keep Python in charge of metadata/options, as native VCF ingestion does.

7. MEDIUM-HIGH / CONFIRMED REPRESENTATION: the frontend repeatedly turns trees
   into JSON and back during expression construction.
   Source: python/vail/expressions.py Expression.__init__, _ir, to_ir; nearly every
   compositional helper calls to_ir on its children and constructs another JSON
   string. Immutability is good, but JSON is being used as the in-memory AST.
   A sequential chain of n operators repeatedly traverses prior prefixes, giving
   quadratic construction/serialization work; reused children become copied trees.
   Runtime type inference also recursively revisits these trees. Store immutable
   typed nodes with shared children, binding/source IDs, and memoized type data.
   Serialize only at the FFI boundary. This should precede adding more ad hoc
   expression-size guards, and preserve the current protection against mutation.

8. MEDIUM-HIGH / DESIGN: logical types ride on incidental Arrow child metadata.
   Sources: ordering/lib.rs, Python arrow.py, execution Type::to_arrow/from_arrow,
   logical_expr.rs restore_type/restore_arrow_array_type, storage normalization.
   A logical descriptor is stored on the first struct child or list element;
   kernel-generated fields can discard it. Python and Rust independently encode
   storage names and descriptors. Restoration/stripping/casting is scattered.
   Existing upstream/native failures around tagged types are supporting evidence,
   but this review does not re-diagnose each one. The representation also has
   asymmetric large-list handling: type_metadata reads LargeList, tag_type only
   tags List, and same_layout handles only List. This is a concrete inconsistency,
   not proof of a specific currently supported LargeList query returning bad data.
   Define one versioned logical-type/storage schema contract, generated/shared
   where possible, and normalize at a few explicit interfaces. Keep logical type
   identity in typed IR independently of Arrow kernels' incidental field names.

9. MEDIUM-HIGH / DESIGN: action resource ownership is fragmented.
   Sources: table/logical.rs session_state constructs a new SessionContext;
   partitioned.rs, globals.rs, text_export.rs and several helpers create default
   TaskContexts. NativeSession primarily owns a Tokio runtime, not a shared query
   session/resource policy. Consequently a coherent host memory/spill/cancellation
   policy is difficult to carry through runtime planning and nested actions.
   This is not a measured OOM finding. Introduce a session-owned execution context
   and an action-owned lifecycle passed through every planner, extension and sink.
   Planning a special operator must not reset the memory budget or object stores.

10. MEDIUM-HIGH / DESIGN: execution replay uses implicit consumer detection.
    Source: table/rng_context.rs, RngContextExec.active/Run.used.
    A repeated request for a partition starts/chooses a new run by examining which
    partition IDs were already requested. Completed runs remain in active, and
    the child is hidden from generic physical traversal. This protects stateful
    repartitioners from optimizer cloning, and the interleaving test is useful.
    But request order is not an explicit action/consumer identity. Uneven consumer
    patterns, early cancellation, and repeated actions deserve a lifecycle model,
    not more partition-request heuristics. No cross-consumer wrong-result repro is
    claimed here. Carry explicit action/consumer scopes and release completed run
    state. Preserve shared DAG inputs within an action and reset only across runs.

11. MEDIUM-HIGH / DESIGN: interval semantics exist in several representations.
    Sources: table/interval_read.rs, provider.rs, join_interval.rs,
    storage/fragment_index.rs, execution interval expression lowering.
    The recent fix appropriately separates candidate selection from physical
    planning. However prefix_interval_predicate has a one-component special case
    and references physical interval fields by numeric position. Provider filter
    normalization/intersection and interval_read have separate bound logic.
    A one-component fast path is legitimate if it implements the same normalized
    bound algebra; currently the common semantic object is not explicit enough.
    Introduce typed key-prefix endpoints and inclusive/exclusive/unbounded bounds.
    Share normalization/comparison rules while distinguishing conservative file
    candidates from exact row membership. Do not force pruning to evaluate data,
    and do not assume a fragment's overlap proves every row matches.

12. MEDIUM / DESIGN: several small compositional APIs imply expensive algorithms.
    Sources: strings.py stepped slicing maps substr over character positions;
    variant.py _min_rep builds ranges and repeated indexed substring comparisons;
    array_methods.py mean filters, widens, sums and counts separate expressions;
    bind is represented as singleton-array map/index rather than a lexical let.
    These are understandable bootstraps but hide allocation/repeated-work costs.
    Stepped Unicode slicing needs a single character traversal; minimal variant
    normalization needs a bounded string kernel; common list statistics need typed
    numeric buffers; lexical binding needs first-class scope. Exact wall-clock or
    quadratic substring cost depends on the underlying kernel and is not measured
    here. Do not replace every composition with a custom UDF—target primitives
    with a clearly worse cost model. The other agent's later numeric-list work
    is outside this branch's reviewed commit and may already address array mean.

13. MEDIUM / DESIGN: relational joins assume more than a shared Arc proves.
    Sources: lookup.rs prepare, zip_join.rs, join_interval.rs.
    Lookup builds one reduced right plan and clones it into each left partition.
    That shares a plan object, not necessarily a cached/replay-safe execution.
    Deferred planning plus repeated right executions can amplify work; interval
    lookup can use NestedLoopJoinExec. This is an execution-cost/replay question,
    not a new measured P-fold scan claim. A common logical join with explicit
    ordering/multiplicity constraints should let the engine own build-side sharing,
    or a Vail operator must own and document that sharing itself. Keep interval
    pruning and native sort-merge joins where their preconditions are established.

14. MEDIUM / CONFIRMED SCOPE OMISSION: my new upstream exclusion policy is incomplete.
    Source: conformance/upstream_scope.py excludes typecheck/, fs/, and
    utils/test_hl_hadoop_and_hail_fs.py, but utils/test_utils.py still contains
    25 test_hadoop_* definitions. Full-run selection is module-only there.
    suite_selection.py independently excludes some of those by name and also
    excludes randomness, which is stale for the full-scope request.
    Thus the prior statement that all Hadoop tests were excluded was too strong.
    Make one scope policy accept module AND definition, apply it consistently to
    collection/inventory/body adapters, and emit explicit excluded reasons. Historical
    reports must retain their original scope. This review records the defect; it
    does not silently change the runners or rewrite historical counts.

15. MEDIUM / DESIGN: tooling can produce precise numbers for incompatible scopes.
    Sources: full_hail_pytest.py, full_hail_bodies.py, suite_selection.py,
    summarize_full_hail.py, report_filtered_suite.py, historical run scripts.
    Preserving raw events, source fingerprints, collection errors, body-only
    outcomes, and unsupported status is good. But scopes, adapted fixtures, error
    classifiers, and counts are implemented in multiple scripts. String matching
    assigns architectural categories from the first exception. The 247-definition
    API bucket demonstrably mixed filesystem/helpers/IO with API gaps. Keep raw
    evidence authoritative, share selection/outcome schemas, and label stale
    reports and alternate body execution unambiguously. A pass count is not an
    architectural approval or a throughput measurement.

WHAT TO KEEP

- Immutable TableIR DAGs and source validation; do not flatten everything into
  Python callbacks or materialized row lists.
- Ordinary DataFusion expressions/operators visible to the optimizer; explicit
  extension boundaries for ordering/partition/identity semantics it cannot model.
- Arrow-buffer adapters for matrix gathers/transposes and coordinate aggregation;
  these are appropriate layout-specific implementations, not inherently hacks.
- Typed Arrow comparison and certified fragment indexes; IPC key bytes are
  transport, not a homemade order encoding.
- Snapshot-pinned lazy local reads and generation-based publication; metadata
  selection is distinct from exact row filtering.
- Bounded producer queues, cancellation tests, GIL detachment for native actions,
  and clear errors at genuinely unsupported capability boundaries.
- A pure counter/context-based RNG primitive and reuse of the same HWE recurrence
  by scalar and aggregate entry points.

IMPLEMENTATION ORDER SUGGESTED BY THIS REVIEW

A. Fix partition restoration first; the 12-row reproducer must preserve actual
   membership, not merely n_partitions(). Define logical partition properties.
B. Establish action-owned resources and replay identities. This is prerequisite
   to making nested plans safely compositional, not an optional performance cache.
C. Converge on logical planning with extension nodes consuming planned children;
   retire legacy compilation one operator at a time, preserving ordering contracts.
D. Share reducer semantics/state across table, matrix-list, collection and scan
   adapters. Replace prefix-rescan and Python full-matrix export implementations.
E. Replace JSON-as-AST and clarify logical type/effect identity. Make optimization
   legal by construction rather than suppressing it with blanket Volatile flags.
F. Consolidate scope/evidence tooling and dependency patch provenance.

These are design changes justified by code invariants. Additional tests should
protect those invariants, but choosing more tests is not a substitute for them.
No product fixes were applied during this review, and no new full-suite pass
count is claimed. The review deliberately includes the author's own recent work.

MODULE LEDGER

The following entries cover every inventoried production module. Related files
are assessed together where they implement one responsibility. 'Retain' means
that the boundary is reasonable, not that every branch is correct. Source paths
below are relative to vail/; inventory.json contains exact fingerprints.

python/vail/__init__.py (2005 lines)
  Table API mixes public dispatch, scope validation, filter-to-interval recognition, aggregation construction and session creation. Extract typed Table/aggregate analysis from the export namespace. _generate is useful composition, but stream/partition lowering determines its cost. See 2, 7, 11.

python/vail/agg.py (217 lines)

python/vail/agg_collections.py (64 lines)
  Good small constructor module; collect/set/take/array-sum options need common identities and ordering/empty semantics rather than planner-specific conventions. See 4.

python/vail/agg_fold.py (52 lines)

python/vail/agg_genomics.py (75 lines)
  Genomic aggregate constructors should remain thin typed wrappers. Allele-count initializer scope and HWE availability must agree across table and matrix-list adapters. See 4.

python/vail/agg_numeric.py (121 lines)

python/vail/allele_functions.py (115 lines)
  Thin expression-based allele classification is maintainable; avoid proliferating callback/index expressions where one shared string primitive would serve. No new correctness defect established.

python/vail/array_aggregate.py (90 lines)

python/vail/array_methods.py (102 lines)
  Fold/scan use explicit lexical parameters and native execution. mean is an allocation-heavy filter/map/sum/count composition in this revision; median sorts all elements. State costs explicitly and use a numeric-buffer kernel where warranted. See 12.

python/vail/arrow.py (281 lines)
  Arrow IPC is a sound FFI boundary and literal-data path. Type tags on child fields and independent storage names make normalization fragile. Large-offset layout compatibility is broader than some Rust helpers. See 8.

python/vail/backend.py (37 lines)
  An explicit native backend is better than pretending to be a JVM. Broad capability strings (matrix_table/randomness) are too coarse to convey reducer/options support. Session should own execution resources. See 9.

python/vail/builders.py (61 lines)
  Conditional builder composition is a reasonable frontend abstraction. Preserve lazy branch/error semantics when lowering; no separate architectural defect isolated.

python/vail/collection_functions.py (153 lines)

python/vail/collections.py (454 lines)
  Collection constructors, native equality restrictions, set/dict tags and function dispatch concentrate useful boundary checks. Many string-named function calls carry a separately asserted dtype. Share a typed operation registry with Rust rather than adding per-API exceptions. See 8.

python/vail/context.py (6 lines)

python/vail/display.py (151 lines)

python/vail/expr/__init__.py (28 lines)

python/vail/expr/expressions/__init__.py (4 lines)

python/vail/expr/expressions/base_expression.py (4 lines)

python/vail/expr/expressions/typed_expressions.py (1 lines)

python/vail/expr/functions.py (29 lines)

python/vail/expressions.py (1385 lines)

python/vail/genetics/__init__.py (5 lines)

python/vail/inputs.py (116 lines)

python/vail/ir/renderer.py (6 lines)

python/vail/linalg/__init__.py (22 lines)

python/vail/lookups.py (93 lines)

python/vail/matrix_list_aggregates.py (480 lines)

python/vail/matrixtable.py (2665 lines)
  Row-owned cell arrays plus global column records are a legitimate matrix layout. Retain physical layout; introduce analyzed matrix operations/properties. See 1, 4, 7.

python/vail/nd.py (35 lines)
  Arrow-backed numeric literals are appropriate. arange creates a tagged struct via expression composition; numerical execution remains a small subset, not a general ndarray engine. Avoid compatibility-shaped APIs implying broader support.

python/vail/qc.py (160 lines)
  Ported variant_qc composed from public expressions is a good boundary. Symbolic matrix column count is appropriate. Scalar HWE reuses native logic, but row reducers still need shared semantics rather than QC-specific support. See 4.

python/vail/queries.py (121 lines)
  Scalar queries eagerly eval their query bounds, while row-indexed queries become lookup joins. Both are defensible strategies but different laziness/cost contracts should be explicit. Dynamic interval lookup cannot assume source pruning. See 11, 13.

python/vail/randomness.py (388 lines)
  Pure random primitives with explicit call-site and dynamic-context inputs are the right core. UID assignment and repeated context rewrites rely on global counters/string markers and consumer-specific lowering. Give identity a typed IR role. See 1, 10.

python/vail/reference_genome.py (291 lines)

python/vail/scan.py (193 lines)
  Reuses aggregate constructors, which is good, but mutates semantics via __vail_scan options and a special fold spelling. Make scan a typed scope/effect, not a convention distributed across dictionaries. See 4, 10.

python/vail/simulation.py (325 lines)
  Porting the Python algorithm avoids inventing a parallel native simulation engine. Its performance and phased compatibility still depend on bind, generation and RNG identities. Do not tune this one workload around compiler deficiencies.

python/vail/streams.py (188 lines)

python/vail/strings.py (245 lines)

python/vail/text.py (255 lines)

python/vail/types.py (827 lines)

Cargo workspace / Python packaging:
  Six crates separate FFI, table planning, execution, storage, VCF and metadata.
  That is a reasonable top-level decomposition. The ordering crate is misnamed;
  table/execution internals still contain several compilers. Cargo.lock pins the
  runtime graph; upstreams.lock.json records research/source provenance and is not
  the same graph. Do not infer built dependency versions from adjacent checkouts.

  extending storage should not mean silently forking transaction behavior.

patches/vortex-array and patches/vortex-layout:
  These are active [patch.crates-io] replacements, so they are production code,
  not merely audit references. The patch README currently explains only Iceberg.

  changes difficult to review independently. For this review I compared both copies
  with the locally cached published 0.86.1 crates and saved vortex-delta.patch plus
  vortex-delta-files.json. Six Rust source files differ; all six deltas were read.
  The copied unchanged upstream modules are NOT certified by this review.

Adjacent Hail/DataFusion/Vortex/Iceberg repositories:
  Consulted as dependency/reference context, not comprehensively reviewed.
  Upstream code size and ownership make a blanket whole-monorepo claim misleading.
  The module ledger covers Vail's own production code and support tools; it is not
  a new quality assertion about millions of third-party lines.

Shell/bootstrap scripts:
  bootstrap_hail_oracle.sh and benchmarks/cloud_bootstrap.sh are environment setup,
  not query implementations. Reproducibility depends on pinned binaries/packages,

Documentation and historical artifacts:
  Documentation is extensive but combines current contracts, early prototype
  descriptions, research plans and dated test counts. For example execution/lib.rs

  checksum expectations disagree across current implementation and older tests.
  Promote a small set of current architecture contracts, link dated evidence as
  evidence, and avoid synthesizing current behavior from whichever old report is
  easiest to find. Generated logs/binary profiles should be external artifacts or

LOCAL VORTEX SOURCE DELTA REVIEW

Base: published vortex-array/vortex-layout 0.86.1 in the local Cargo registry.
This is a crate-content comparison, not a claim of a verified upstream Git SHA.
Packaging differences (omitted crate-local locks/original manifests, added licenses)
are listed separately in vortex-delta-files.json. Runtime source delta is captured
in vortex-delta.patch. No changes to the vendored sources were made by this review.

patches/vortex-array/src/scalar_fn/fns/list_project.rs:
  New nested struct/list projection function. Preserves list offsets/sizes/validity,
  validates paths and bounds serialized path counts/lengths. This is a legitimate
  storage expression primitive, not a matrix-specific name check. Recursive list
  boundaries and nullable structs need a clearly specified path algebra shared
  with scan dependencies. Execution canonicalizes lists; it is not universally
  zero-copy. No new defect was demonstrated in this module.

patches/vortex-array/src/expr/analysis/referenced_field_paths.rs:
  Teaches dependency analysis how Project paths cross list element boundaries.
  Conservative whole-root fallback for non-root input is appropriate. This forms
  a paired contract with list_project and layout readers; extending only one half
  can produce wrong pruning or decode-all behavior.

patches/vortex-array/src/scalar_fn/fns/mod.rs:
  Exports the new projection module. Mechanical registration boundary.

patches/vortex-array/src/scalar_fn/session.rs:
  Registers Project for serialization/execution. Appropriate; persisted expressions
  using vortex.list.project require a reader with this extension, so compatibility
  and upstreaming/version policy should be explicit.

patches/vortex-layout/src/layouts/list/reader.rs:
  Pushes root Project into the element reader and retains list offset/validity
  ownership. Good division of responsibility; avoids an extra projection after
  elements are already narrowed. Non-root expressions retain the generic path.
  Added test rejects actual reads of a pruned leaf segment: stronger evidence of
  IO pushdown than an explain assertion alone. All-row and masked paths are both
  changed; there is no claim here of exhaustive mask/layout correctness.

patches/vortex-layout/src/layouts/struct_/reader.rs:
  Adds nested Project expansion and preserves root nullable-struct validity using
  masks, including is_null/is_not_null rewrites. These are semantic changes beyond
  a performance projection. Maintaining the parent null bitmap while projecting
  child fields is essential. This patch should be upstreamed/documented as such,
  with explicit nullable-root/child contracts, rather than described only as field
  pruning. No new corruption repro was established.
