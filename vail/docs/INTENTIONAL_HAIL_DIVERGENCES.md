# Intentional semantic differences from Hail

This records deliberate changes to Hail semantics. An entry describes the intended Vail behavior, not necessarily the current implementation.

- **Partitioning (decided 2026-10-15; implementation pending):** Partition layout is an execution/storage choice for DataFusion/Vail, not a Hail compatibility contract. Preserve predicate and interval-filter pushdown through to Vortex, avoiding reads of files and segments whose bounds/statistics prove they cannot match. Verify pruning by observing or rejecting unnecessary reads, separately from checking returned rows; exact Hail partition counts are not evidence of pruning. Preserve partitioned table storage with sorted, key-range-disjoint files produced by a DataFusion/Vail parallelism strategy; do not collapse table storage into one giant Vortex file. Explicitly stop supporting the `_n_partitions` read option, `_filter_partitions`, and writing a MatrixTable with explicit partition intervals (`_partitions`). This decision does not yet specify replacement APIs, exact file sizes/counts, or the future behavior of other partition-related APIs. See the [partitioning decision](PARTITION_COMPATIBILITY.md#vail-partitioning-decision-2026-10-15). Existing implementation and historical tests may still enforce superseded Hail behavior until the implementation is changed.

- **Population standard deviation (implemented):** Use DataFusion's population standard deviation accumulator with Arrow centering to avoid catastrophic cancellation for large offsets. This applies to `stats.stdev`, grouped aggregation, and scans. For example, `[1e12, 1e12 + 1, 1e12 + 2]` returns approximately `0.816497`; the live Hail oracle returned `0`. Empty inputs still return NaN, missing values are ignored, finite singletons return zero, and present NaNs or infinities propagate NaN. Other `stats` fields retain their existing behavior. See [P1 regression tests](../python/tests/test_p1_review_fixes.py).

- **Native DataFusion floating-point semantics:** Use DataFusion/Arrow operators directly for comparisons, sorting, grouping, and joins. Do not encode float operands as custom comparison keys or add float wrappers. This replaces the previous requirement for uniform bitwise equality across operators. Arithmetic keeps the ordinary Float32/Float64 representation.
  - **Scalar signed-zero equality:** `-0.0 == +0.0` is true in native scalar expressions. Native scalar grouping and join keys consequently treat the two zeros as the same value. This agrees with Hail's signed-zero equality, but supersedes Vail's earlier distinct-zero policy.
  - **Nested equality:** Native comparisons of arrays, tuples, and structs can distinguish signed zeros in their members; for example, `[-0.0] == [+0.0]` is false. Vail accepts this library behavior rather than imposing Hail's recursive equality rule or normalizing nested values.
  - **NaN key equality:** Native ordering/key comparisons can distinguish NaN signs, payloads, and signaling/quiet bits, unlike Hail's all-NaNs-equal key equivalence. This applies to grouping and joins as provided by the pinned library. Vail does not collapse all NaNs to a canonical value.
  - **Missing operands:** A scalar comparison with an outer missing operand returns missing. Nested missing values follow the native comparison kernel. Sorting follows native DataFusion/Arrow ordering.
  Library behavior is recorded in [DataFusion ordering audit](DATAFUSION_ORDERING_AUDIT.md); its proposed float wrapper is superseded by this decision.

- **Set/Dictionary ordering and keying (unsupported):** Reject ordering comparisons and Table keys, sorting, and grouping keys containing sets or dictionaries, including nested occurrences. Equality and ordinary collection operations, including Set subset/superset operators, remain available. Do not implement custom ordering/key encodings to support these domains; revisit their representation and supported operations later.

- **Missing-value ordering (decided; implementation pending):** Adopt Vortex's missing-first ordering for nested values instead of Hail's missing-last ordering: for example, `[missing] < [1]` and `struct(x=missing) < struct(x=1)`. Two nested missing values compare equal. Use library comparison kernels rather than adding a compatibility adapter for Hail's null placement, preserving throughput and predicate pushdown. Comparisons with a missing outer operand still return a missing boolean; this decision does not replace three-valued expression semantics. Keep ordering consistent across keys, sorting, grouping, joins, and fragment bounds. Vail's current comparator still orders missing values last; adoption requires a new comparator version and rebuilt bounds. See [comparison audit](VORTEX_COMPARISON_AUDIT.md).
- **`hl.agg.approx_cdf` (implemented):** Reject both public and `_raw=True` calls explicitly. The current sketch library does not expose Hail-compatible retained items and per-level compaction state; Vail does not return a partial or fabricated CDF schema. `approx_quantiles` and `approx_median` remain supported.
- **Approximate quantile sketch size (implemented):** Reject `k > 65535` for `approx_quantiles` and `approx_median`, reflecting the current library's `u16` parameter limit. Hail accepts `k=65536`: a live check on `[0, 1, 2, 3]` returned median `2` and quantiles `[0, 2, 3]`. No explicit `k=65536` case was found in the pinned Hail Python or Scala test sources; its quantile tests exercise default `k` and `k=200` rather than that boundary. This is a documented Vail limitation, not a Hail restriction.
- **JVM hexadecimal floating-point string parsing (current incompatibility):** Vail's Arrow/DataFusion-backed `hl.float32`, `hl.float64`, and `hl.float` casts do not accept JVM hexadecimal float strings. These spellings use `0x`/`0X`, a hexadecimal significand, and a required `p`/`P` exponent whose decimal number specifies a power of two. Examples include `0x1.0p0` (1.0), `0x1.8p1` (3.0), `-0x1.0p-1` (-0.5), and `+0X1.AP+2` (6.5). A decimal point is optional (`0x1p0`); JVM parsing also accepts suffixes `f`, `F`, `d`, and `D`, such as `0x1p0f` and `0x1.0p0D`. These strings are currently rejected by Vail with an evaluation-time `RuntimeError`, rather than parsed to their numeric values. `hl.parse_float32`, `parse_float64`, and `parse_float` remain explicitly unimplemented and raise `NotImplementedError`. This records a present limitation, not a commitment to permanently diverge. Python numeric inputs and ordinary decimal-string casts are unaffected. See [JVM parsing grammar](https://docs.oracle.com/en/java/javase/24/docs/api/java.base/java/lang/Double.html#valueOf(java.lang.String)) and [string-operation limitations](STRING_OPERATIONS.md).


- **Deferred ndarray operations and scope diagnostics:** ndarray indexing, reshape, matrix multiplication, ordering comparisons, and keying raise `NotImplementedError` for otherwise valid expressions. Unkeyed ndarray values still round-trip through Arrow and table storage. A row- or column-scoped ndarray validates operand scopes first, preserving the upstream cross-axis diagnostics. Literal/global ndarray bases reach the unsupported-operation error before a surrounding MatrixTable operation can validate its result scope. These checks do not implement ndarray execution.
