# Intentional semantic differences from Hail

This records deliberate changes to Hail semantics. An entry describes the intended Vail behavior, not necessarily the current implementation.

- **Floating-point ordering (implemented):** Use IEEE 754 `totalOrder` for `float32` and `float64`, including the ordering of NaNs by sign and bit pattern and the distinction between negative and positive zero. Apply this consistently to sorting, key grouping, joins, and storage fragment bounds. Hail's key comparator treats all NaN bit patterns as equal; Vail intentionally distinguishes them. Expression comparisons and set ingestion use the same total-order encoding; present floats compare equal exactly when their bits match. See [Key ordering](KEY_ORDERING.md).
- **Missing-value ordering (decided; implementation pending):** Adopt Vortex's missing-first ordering for nested values instead of Hail's missing-last ordering: for example, `[missing] < [1]` and `struct(x=missing) < struct(x=1)`. Two nested missing values compare equal. Use library comparison kernels rather than adding a compatibility adapter for Hail's null placement, preserving throughput and predicate pushdown. Comparisons with a missing outer operand still return a missing boolean; this decision does not replace three-valued expression semantics. Keep ordering consistent across keys, sorting, grouping, joins, and fragment bounds. Vail's current comparator still orders missing values last; adoption requires a new comparator version and rebuilt bounds. See [comparison audit](VORTEX_COMPARISON_AUDIT.md).
- **`hl.agg.approx_cdf` (implemented):** Reject both public and `_raw=True` calls explicitly. The current sketch library does not expose Hail-compatible retained items and per-level compaction state; Vail does not return a partial or fabricated CDF schema. `approx_quantiles` and `approx_median` remain supported.
- **Approximate quantile sketch size (implemented):** Reject `k > 65535` for `approx_quantiles` and `approx_median`, reflecting the current library's `u16` parameter limit. Hail accepts `k=65536`: a live check on `[0, 1, 2, 3]` returned median `2` and quantiles `[0, 2, 3]`. No explicit `k=65536` case was found in the pinned Hail Python or Scala test sources; its quantile tests exercise default `k` and `k=200` rather than that boundary. This is a documented Vail limitation, not a Hail restriction.
- **JVM hexadecimal floating-point string parsing (current incompatibility):** Vail's Arrow/DataFusion-backed `hl.float32`, `hl.float64`, and `hl.float` casts do not accept JVM hexadecimal float strings. These spellings use `0x`/`0X`, a hexadecimal significand, and a required `p`/`P` exponent whose decimal number specifies a power of two. Examples include `0x1.0p0` (1.0), `0x1.8p1` (3.0), `-0x1.0p-1` (-0.5), and `+0X1.AP+2` (6.5). A decimal point is optional (`0x1p0`); JVM parsing also accepts suffixes `f`, `F`, `d`, and `D`, such as `0x1p0f` and `0x1.0p0D`. These strings are currently rejected by Vail with an evaluation-time `RuntimeError`, rather than parsed to their numeric values. `hl.parse_float32`, `parse_float64`, and `parse_float` remain explicitly unimplemented and raise `NotImplementedError`. This records a present limitation, not a commitment to permanently diverge. Python numeric inputs and ordinary decimal-string casts are unaffected. See [JVM parsing grammar](https://docs.oracle.com/en/java/javase/24/docs/api/java.base/java/lang/Double.html#valueOf(java.lang.String)) and [string-operation limitations](STRING_OPERATIONS.md).
