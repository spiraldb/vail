# Hail Table contract audit (planning baseline)

**Source snapshot:** `hail-is/hail` commit [`e10cc355bc8cd0de9c5f29d5182d31527898bae1`](https://github.com/hail-is/hail/tree/e10cc355bc8cd0de9c5f29d5182d31527898bae1), audited from `hail/python/hail/table.py` and the cited Python/Scala IR files. The generated public API inventory is [hail-api-inventory.json](hail-api-inventory.json); its stdlib-only generator is [inventory_hail_api.py](../../scripts/inventory_hail_api.py). This is a compatibility plan, not a claim that Vail currently implements Hail parity.

## Compatibility checklist

### Row identity, key ordering, and order

- [ ] Model key as an ordered list of named typed fields, not just a uniqueness constraint. Hail's `key` property exposes the key struct; key fields remain part of `row` and are excluded from `row_value` ([`Table.key`, `row`, `row_value`](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L436), [row properties](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L4147)).
- [ ] `key_by` defines a new key and sorts ascending by the key. The docs call re-keying expensive because it sorts; key shortening leaves relative order among equal keys undefined. An empty key leaves row order undefined. Never test or promise a deterministic order within duplicate keys ([`key_by` docs/implementation](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L750)). The source backend uses a distributed `TableKeyBy`; exact tie order/partition placement is not promised.
- [ ] A key expression passed positionally must be a field reference (possibly nested); computed expressions need a keyword name. Key names are collision-checked. See [`get_key_by_exprs`](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/utils/misc.py#L415).
- [ ] `order_by` accepts fields/expressions, asc/desc, lexicographically orders arguments, and removes the key. Missing values sort after defined values; the Scala comparison explicitly places missing after non-missing and its descending wrapper reverses only non-null comparisons ([`order_by`](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L3706), [`CodeOrdering`](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/hail/src/is/hail/expr/ir/orderings/CodeOrdering.scala#L216)).
- [ ] Do not silently assert stability for equal sort keys. Hail documents field sort precedence and null placement but does not promise tie ordering. The actual distributed sort can depend on execution and partitioning.
- [ ] `head(n)` / `take(n)` operate on the beginning of the table's current order; `tail(n)` on its end. Preserve non-negative `n` validation and row sequence. Hail says head/tail result partition count is the count of source partitions touched by the selected rows ([`head`, `tail`, `take`](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L2994), [IR validation](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/hail/src/is/hail/expr/ir/TableIR.scala#L2157)). Vail should preserve row semantics; partition count is an execution property whose exact matching requires separate evidence.
- [ ] `add_index(name='idx')` creates an int64 zero-based index following current row traversal order, so it is deterministic only to the extent the input order is defined ([`add_index`](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L2870)). A newly assigned index should not be treated as stable across re-keying, shuffling, or unkeyed execution.

### Nulls, duplicates, union, joins, and indexing

- [ ] Missing key components are valid values for ordering/index behavior, but joins explicitly do not match missing key values. Keep ordering null semantics separate from join equality ([`join` contract](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L3397)).
- [ ] `union` preserves duplicate rows; exact row type/key name and type must match unless `unify=True` reconciles fields and inserts missing values. Schema unification may widen compatible types and rejects incompatible types ([`union`](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L2916)). The public docs do not spell out output ordering. In the current keyed execution path, Hail lowers keyed union by merging streams over the key comparator, and the direct execution path calls `RVD.union` with key length ([`TableUnion` lowering](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/hail/src/is/hail/expr/ir/lowering/LowerTableIR.scala#L1626), [relational execution](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/hail/src/is/hail/expr/ir/lowering/ExecuteRelational.scala#L131)). Treat ascending key order for keyed union as source-observed backend behavior to pin with an oracle; equal-key tie order and unkeyed union order remain unspecified. Partition layout is not a contract.
- [ ] `Table.join` is a Cartesian product for duplicate matching keys. Its documented/public behavior joins the full keys: key arity and corresponding key types/order must agree; names may differ. The result retains the left key names/order; left/right/inner/outer missing-side behavior is defined; missing keys never match. Right value-field conflicts are renamed by the Python wrapper ([`join` docs and signature](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L3397)). The `_join_key` underscore argument allows an internal partial-prefix join in the Python implementation, but this is not part of the documented public contract. At the IR level, output key schema retains left key fields and appends right suffix fields; Scala warns partial-prefix joins can produce out-of-order keys for certain duplicate-key configurations ([Scala schema and caveat](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/hail/src/is/hail/expr/ir/TableIR.scala#L2206)). Keep the private partial-prefix case labeled as implementation behavior and out of public parity claims.
- [ ] `semi_join`/`anti_join` filter left rows by whether a prefix of left key exists in the right table's non-empty key; right key length may be shorter and types must match ([`semi_join`/`anti_join`](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L3260)).
- [ ] `index`/`table[key]` is an expression-level left lookup returning the indexed table's `row_value` (key fields removed); no match yields missing. A prefix of a key can be flex-indexed; `all_matches=True` is experimental and produces an array. Index expressions are scoped to the caller's row/global axis; indexing with values from a MatrixTable row or column context is supported by separate IR paths, while entry-based MatrixTable joins raise `NotImplementedError` ([`index` docs and implementation](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L2377), [index IR dispatch and boundaries](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L2495)). For duplicate keys, ordinary Hail keyed lookup is not an all-matches operation; avoid specifying which duplicate value is selected unless confirmed by backend behavior. `all_matches` explicitly requests all matches.

### Aggregation, globals, and expression source semantics

- [ ] `group_by` makes named row-key expressions; positional strings/expressions must refer to fields, while arbitrary expressions are accepted by name. Aggregations belong in the subsequent `.aggregate`; key expressions do not support aggregation. Result has group fields as key and named aggregate fields as values; names must not collide ([`group_by`](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L1783), [`GroupedTable.aggregate`](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L253)).
- [ ] Group aggregate output ordering is by group key, but equal group rows collapse to one. `partition_hint(n)` is a target partition count for aggregation; default is upstream partition count. This is a performance hint, not observable row semantics. The internal buffer size is private and not part of public API ([`partition_hint`](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L197)).
- [ ] `aggregate(expr)` reduces across rows to a local value by default and can return a Hail expression when `_localize=False`; row aggregations are expected. `count()` counts rows ([`aggregate`](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L1879), [`count`](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L498)).
- [ ] Hail expressions carry source indices. `Table.row` fields are row-indexed; `Table.globals` fields are global-indexed. Operations analyze expressions against allowed axes. For example, GroupedTable aggregate expressions are analyzed against parent globals plus rows, and `Table.index` checks expressions against the calling Table row axis or MatrixTable row/column context. Preserve axis errors; do not collapse globals into row fields or permit cross-source expressions accidentally ([properties](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L4147), [expression analysis](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/expr/expressions/expression_utils.py#L13), [group aggregation validation](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L253)).
- [ ] Globals are table-level fields, accessible from `ht.globals`, preserved by row transformations unless explicitly selected/annotated; joins combine global types and union type is represented by the first child in the Python IR. Global values for multi-input union should be oracle-tested; public `union` documentation does not state value conflict policy. Do not invent one ([`Table.globals`](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L4147), [join result type](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/hail/src/is/hail/expr/ir/TableIR.scala#L2234), [TableUnion typing](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/ir/table_ir.py#L142)).

### Partition behavior

- [ ] Preserve APIs and meaningful requested controls (`n_partitions`, `repartition(n, shuffle=...)`, `naive_coalesce`, `GroupedTable.partition_hint`) and expose a partition count where feasible. Hail describes shuffle repartition as equal-sized and non-shuffle as coalescing existing partitions; non-shuffle cannot increase partition count. Naive coalesce combines adjacent partitions and may be imbalanced ([`repartition`](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L3159), [`naive_coalesce`](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L3229)).
- [ ] Partition count, boundaries, shuffle tie order, file partitioning, and scheduling are execution-plan effects. Match exact counts only where the API explicitly guarantees them (e.g. `head`/`tail` docs); avoid treating the current Hail/Spark partition plan as universal semantics.

## Explicit scope boundaries (must be surfaced)

- `Table.to_matrix_table(...)` and `Table.to_matrix_table_row_major(...)` return a `MatrixTable`; `_unlocalize_entries` is an internal Table-to-Matrix conversion. They are not Table-returning operations and require an explicit MatrixTable scope/compatibility decision ([conversion methods](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L3921), [private conversion](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L4581)). There are no Table API methods returning a `BlockMatrix` in this source module.
- `Table.from_spark`/`to_spark` are Spark-specific interop and depend on `pyspark`/`Env.spark_backend`; they cannot be advertised as native Rust Table operations without an explicit Spark adapter. Hail imports `pyspark` at module import time ([module imports](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L1), [Spark methods](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L4217)). Pandas interop is a separate conversion path, not Spark, but may materialize locally ([`to_pandas`/`from_pandas`](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L4280)).
- `Table.index` has MatrixTable row/column paths; entry-axis indexing is explicitly unsupported. `MatrixTable`/`GroupedMatrixTable` operations mentioned in `BaseTable` docs or `group_by` docs are not Table methods and should not be counted as Table compatibility.
- The compact research inventory is generated from direct public `Table` and `GroupedTable` AST members. Inherited `BaseTable` behavior and Python protocols are audited separately in the expanded C1 ledger; notably `BaseTable.__iter__` errors and dynamic field access, mutability errors in `__setattr__`/`__delattr__`, and `__getitem__` field/index dual semantics ([`BaseTable`](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L129), [`Table.__getitem__`](https://github.com/hail-is/hail/blob/e10cc355bc8cd0de9c5f29d5182d31527898bae1/hail/python/hail/table.py#L423)).

## Oracle test cases for the native backend

Compare schemas and values against this pinned Hail checkout. Compare ordered sequences only when Hail defines order; otherwise compare multisets, and never assert which equal-key duplicate is first.

1. **Key ordering/nulls:** rows with keys `(2,'b'), (missing,'a'), (1,'z'), (2,'a')`; `key_by('k1','k2')`; assert lexicographic order and Hail null placement. Re-key by `k1` and assert groups contiguous without an intra-`k1` tie-order assertion.
2. **Unkeyed and equal sort ties:** `key_by()` and `order_by('sort')` on repeated/null `sort`; assert key removal, primary sort, and missing placement, but allow permutation within equal defined values and equal nulls.
3. **Order transforms:** sort by a unique full tuple such as `order_by(desc('a'), asc('b'), asc('unique_id'))`, then `head(0)`, `head(2)`, `tail(2)`, `take(2)`; compare exact sequence. If the full sort tuple has ties, compare tied rows permissively because Hail does not promise stable tie order.
4. **Index and add_index:** unique keyed lookups (hit/miss), key-prefix lookup, compound-key lookup, `all_matches=True` on duplicate keys, and lookup with missing values. After a deterministic `order_by`, assert zero-based int64 `add_index`; after unkeyed/repartition transformations, do not require IDs to follow an unspecified ordering.
5. **Duplicate joins:** left has two rows at key 1; right has three; public full-key inner join must produce six matched pairs. Also exercise all four public join types, missing key on both sides (must not match), conflicting value-field names, and different key field names. If `_join_key` implementation behavior is tracked, isolate its partial-prefix case in a separate private-compatibility test and allow the documented IR warning about out-of-order result keys.
6. **Semi/anti join prefix:** left compound key `(a,b)` and right key `(a)`; assert filter membership, duplicate left rows preserved, empty right-key rejection, and type/arity errors.
7. **Union:** duplicate row in both sides remains twice; exact schema union and `unify=True` with a missing field and compatible numeric widening; reject incompatible field type/key. For keyed inputs, assert source-observed ascending key order while allowing any ordering among equal keys. For unkeyed inputs, compare as multisets.
8. **Grouped aggregation:** groups with repeated and missing keys, empty input, multiple aggregation outputs, name collision, `partition_hint`, `count`, sum/mean, and global field referenced in aggregate. Assert grouped output key order and aggregate values, not partition count unless requested contract covers it.
9. **Axis errors/globals:** annotate/select using row and global expressions; ensure row expressions do not silently broadcast across unrelated tables and global fields remain global. Check `index` from another Table row expression succeeds, while entry-scoped MatrixTable indexing reports the documented unsupported case if matrix support is present.
10. **Partitions:** test requested `range_table`/`parallelize` partition counts, shuffle/coalesce constraints, `naive_coalesce`, and `head`/`tail` exact result counts. Treat boundaries and task scheduling as non-oracle values.

## Proposed Luna implementation work package

Luna owns the **compatibility inventory, API mapping, and typed oracle fixtures**. Sol owns the semantic kernel and native operators. Luna’s bounded package is:

1. Complete the Table/GroupedTable method-to-Hail-IR/API mapping, including signatures, expression axes, return types, documented behavior, implementation-only behavior, and explicit MatrixTable/Spark boundaries. Record inherited protocols separately from the direct AST inventory.
2. Define typed oracle fixtures against this pinned Hail commit for keys, nulls, duplicate joins, union ordering, indexing, scans, globals, and partition-sensitive operations. Mark every assertion as documented contract, source-observed backend behavior, or unspecified behavior.
3. Deliver the mapping, fixture definitions/results, and explicit known gaps. Do not implement Rust comparators, operators, or execution semantics in this Luna package; those belong to Sol.

## Open questions for the parent design

- Will native Vail promise Hail's incidental physical order for any operation, or only semantic ordering backed by keys/`order_by`? Hail explicitly leaves equal-key and no-key order undefined, so avoiding accidental promises is critical.
- What are Hail's observed globals values for unions with unequal globals? Public docs do not specify; probe the pinned Hail oracle before defining Vail behavior.
- Should Python compatibility retain importable `hail.table` without PySpark? Hail's module currently imports `pyspark` at top level; a native backend can preserve method APIs while isolating or replacing Spark-specific imports.
- How much partition introspection must Vail match beyond `n_partitions()` and explicit controls, given Arrow/Vortex may have different physical boundaries?
