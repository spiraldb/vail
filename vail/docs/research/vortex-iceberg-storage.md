# Vail storage: Vortex, Iceberg, and ordered table scans

Research pinned to Vortex `32895ce81dc160155d8c77bdafb58694b2a2a8a4`, Apache Iceberg `5e7169168db3d34e29354c6f59ec4d6e420b8d2d`, iceberg-rust `c9a25b23b7645f3af0e9dfd7e85d8cf646901c55`, and DataFusion `23f6f94c308a800748a5f8b7a5b85d5e41e5dc95` (local checkouts in `../../../vortex`, `../../../iceberg`, `../../../iceberg-rust`, and `../../../datafusion`). These are the original main-branch code/specification observations. The implementation decision below has been updated to use an existing upstream PR rather than implement another integration.

## Decision and compatibility boundary

Use a real Iceberg snapshot as the authority for the live data-file set and an immutable, snapshot-bound Vail descriptor for Hail semantics, globals, and a required fragment interval index for persisted ordered tables. Reuse [apache/iceberg-rust PR #2835](https://github.com/apache/iceberg-rust/pull/2835) at `0252fe9174aa3062da51328c444a765aa7de2dae` for Vortex support: `VortexWriterBuilder`, embedded Iceberg schema, field-ID-aware reader and format dispatch. Do not reimplement those components in Vail. The PR uses Vortex `0.86.1` and Arrow `59.2`; pin its actual cohort. Keep only Vail snapshot metadata hooks in a separate patch. Iceberg metadata/manifests retain JSON/Avro encodings; files are marked `VORTEX`. This upstream preview does not establish arbitrary-engine interoperability. See the [PR ordering review](iceberg-pr-2835-ordering.md) for the actual reader path; the develop-branch Vortex adapter observations below are historical context, not proof of PR reader behavior.

The Iceberg spec's manifest `file_format` field lists `avro`, `orc`, `parquet`, and `puffin` (`iceberg/format/spec.md:721`). Java's `FileFormat` enum has no Vortex (`iceberg/api/src/main/java/org/apache/iceberg/FileFormat.java:26-31`). Rust's `DataFileFormat` has those four variants and rejects unknown strings (`iceberg-rust/crates/iceberg/src/spec/manifest/data_file.rs:380-411`). Its public generic `FileWriterBuilder`/`FileWriter` traits are a possible write adapter seam (`iceberg-rust/crates/iceberg/src/writer/file_writer/mod.rs:39-51`), but the current Arrow reader opens Parquet directly (`iceberg-rust/crates/iceberg/src/arrow/reader/pipeline.rs:148-155`) and constructs a `ParquetRecordBatchStreamBuilder` (`:288`). Adding a writer alone is therefore insufficient. Existing Java and Rust Iceberg readers will reject or fail to read the new format until extended. Never label Vortex bytes as `PARQUET` or place the only row data in an optional sidecar. Iceberg-rust's version is `0.10.1` and Arrow is `59.2` (`iceberg-rust/Cargo.toml:37,51-59`); Vortex HEAD uses Arrow `59.2` and DataFusion `55.0.0` (`vortex/Cargo.toml:105-114,143-159`). The independently cloned DataFusion HEAD uses Arrow `60.0.0` and DataFusion `55.1.0` (`datafusion/Cargo.toml:93,126`), so do not mix HEAD with these pinned crates without a version alignment spike.

## What ordering Iceberg and Vortex actually provide

Iceberg sort metadata describes sorting **within a data or delete file**, including source field IDs, transform, direction, and null placement. The default order is a writer hint and writers are not required to obey it (`iceberg/format/spec.md:640-655`). Missing or unknown file sort ID means unsorted (`:753`). Neither sort IDs nor manifest order certify a global iteration order. Snapshots are the union of live files across reusable manifests; manifests can cover arbitrary subsets and are not partition bound (`iceberg/format/spec.md:82-89,986-1014`). Iceberg sequence numbers represent relative commit age for data/delete application, not lexicographic row position (`:102-106`). Manifest order and physical listing order must never implement Hail's ordered-key contract.

Vortex has an explicit ordered-scan flag (`vortex/vortex-scan/src/lib.rs:142-144`). Its multi-file scan preserves the supplied child order when that flag is true (`vortex/vortex-layout/src/scan/multi.rs:403-433`), and its layout scan uses `buffered` rather than `buffer_unordered` for ordered chunks (`vortex/vortex-layout/src/scan/scan_builder.rs:447-455`). These are **preservation** facilities, not proof that source rows are key-sorted. The current DataFusion v2 adapter is not an ordered-table implementation: it defaults to unordered, requests ordered scanning only when handed an ordering hint, and still flattens partitions using `try_flatten_unordered` (`vortex/vortex-datafusion/src/v2/source.rs:277,352-353,405-432,491-499`). Its `eq_properties` reports no output ordering (`:504-506`). Vail must provide ordered fragment scheduling when storage order matters. Whole-table sorting is not an allowed read fallback. It must not advertise ordered output to DataFusion based solely on an Iceberg sort order ID.

Vortex's usable single-file APIs are `VortexWriteOptions::write` over an `ArrayStream` or its push writer (`vortex/vortex-file/src/writer.rs:80-98,223-230,361-369`), `VortexOpenOptions::open`/`open_path` (`vortex/vortex-file/src/open.rs:219-240`), and `VortexFile::scan`/`data_source` (`vortex/vortex-file/src/file.rs:206-224`). The multi-file builder discovers globs (`vortex/vortex-file/src/multi/mod.rs:32-50,120-170`), which is unsuitable as the authority for an Iceberg table's snapshot; an Iceberg scan must use only the live files in the pinned snapshot. `VortexTable` adapts a `DataSourceRef` into a DataFusion `TableProvider`, with an Arrow schema supplied by the caller (`vortex/vortex-datafusion/src/v2/table.rs:89-107,111-150`).

Schema translation requires a separate compatibility gate. Iceberg projects by stable field ID across renames and reorderings; its Arrow schema conversion expects field IDs in Arrow field metadata (`iceberg-rust/crates/iceberg/src/arrow/schema.rs:291-302,320-329`). The existing Rust Parquet reader resolves embedded IDs, name mapping, or positional fallback (`iceberg-rust/crates/iceberg/src/arrow/reader/pipeline.rs:157-199`). Vortex DataFusion's physical-schema reconciliation copies metadata from a caller-supplied reference Arrow schema by **field name** (`vortex/vortex-datafusion/src/convert/schema.rs:20-63`); this alone is not Iceberg ID-based evolution. It recurses through structs and maps to preserve some Arrow extension metadata (`:95-125,185-226`), while Vortex's non-session Arrow dtype conversion warns that non-builtin extension metadata can be stripped (`vortex/vortex-arrow/src/dtype.rs:80-92`). Vail's bridge must build a field-ID mapping from the snapshot schema, verify nested IDs and names, and test extension and Hail logical-type round trips. A missing or mismatched ID must not silently become a same-position column.

## Proposed snapshot-bound Vail descriptor

Store a small immutable descriptor object under Vail's metadata prefix and place its URI plus content hash in namespaced **snapshot summary properties**. Iceberg-rust exposes custom append snapshot properties (`iceberg-rust/crates/iceberg/src/transaction/append.rs:70-71`), which its snapshot producer copies into the summary alongside computed metrics (`iceberg-rust/crates/iceberg/src/transaction/snapshot.rs:399-418`). This is an application protocol, not an Iceberg ordering feature. Prefer a single descriptor that references optional larger run-index and globals objects; never put large data in the summary. The descriptor contains:

* protocol version, table UUID, snapshot ID, schema ID/hash, partition spec IDs, comparator version and key field IDs (plus transform/direction/null semantics), and a fingerprint of the complete live data/delete-file set;
* Hail logical-type schema and metadata required to reconstruct semantics, including a durable globals object pointer/hash and a distinction between missing globals and an empty globals value;
* a required key-interval index for persisted keyed/explicitly ordered tables, each fragment carrying immutable data-file URI, content hash or object generation, row count, first/last key, and declared intra-file sorting. For a pure concatenation order, adjacent run bounds must satisfy `last(left) <= first(right)` under the exact Hail comparator. If ranges overlap, the descriptor must declare a supported streaming merge plan; unsupported order metadata fails the read and requires explicit repair. Tie behavior must be specified if equal keys occur across runs.

Hail semantic metadata is required for a Vail table read. A missing or corrupt descriptor, logical type, key, comparator, or globals object is an error, even if rows can be read as Arrow. An absent or invalid required **key-interval index** fails the ordered read; reconstruction/reclustering is an explicit operation outside the read path. No whole-table read-sort fallback is allowed. Row filters, projection, delete files, and compaction need careful handling: an order-preserving filter remains ordered; projections that drop the key may retain underlying order but cannot advertise key ordering; row rewrites and unknown external writers invalidate the certificate. When equality/position deletes appear, Vail must apply their Iceberg semantics before claiming table contents, preserving relative row order and valid interval metadata; until implemented, it must reject those snapshots. For mixed partition specs and external writes, recompute from the complete live file set rather than inheriting a prior certificate.

Write data and descriptor objects first, then commit the snapshot and its descriptor pointer via the catalog's atomic metadata swap (`iceberg/format/spec.md:78-99,1138-1142`). Readers pin a snapshot ID, resolve only **that snapshot's** summary pointer, verify hash/identity and the live file-set fingerprint, and never consult a mutable `latest` sidecar. On an optimistic conflict/retry, rebuild the descriptor and order certificate against the new base and publish a new pointer in the successful snapshot; abandoned objects remain unreachable and are garbage-collected later. An external writer's new snapshot will lack a matching descriptor: Vail must reject Hail semantic reads until a migration/reconciliation commit reconstructs the required metadata. A compaction must write a fresh certificate, with new file bounds, even when logical rows are unchanged. Retain descriptor, run-index, and globals objects for every reachable Iceberg snapshot and branch/tag; expire them only after their referencing snapshots are no longer retained. Snapshot expiration and orphan-file cleanup need explicit Vail object marking because generic Iceberg cleanup will not discover arbitrary sidecars.

The stock iceberg-rust fast-append API accepts summary properties before its internal `SnapshotProducer` generates the snapshot ID (`iceberg-rust/crates/iceberg/src/transaction/append.rs:70-94`; `iceberg-rust/crates/iceberg/src/transaction/snapshot.rs:116-135`). A descriptor that embeds the committed snapshot ID and exact live-file fingerprint therefore needs a Vail commit coordinator or a narrowly scoped producer hook that prepares the descriptor after the snapshot ID and effective base are known, before the metadata commit. This is a real implementation dependency, not something `set_snapshot_properties` alone solves. If the hook cannot be made atomic with the snapshot summary, reject the commit and keep the sidecar unreachable; never publish a pointer and fill in the sidecar later.

## Scoped implementation tasks for Sol

1. Pin a single Arrow/DataFusion dependency set and prove Vortex + iceberg-rust can coexist in one crate. If DataFusion HEAD is desired, resolve its Arrow 60 mismatch first; do not defer that to feature work.
2. Integrate PR #2835's existing Vortex writer and Iceberg reader/scan dispatch. Preserve its embedded field-ID schema and real DataFile metrics; remove Vail's direct Vortex file codec path. Keep unsupported-delete rejection in Vail until the descriptor/order protocol handles deletes, even where the PR supports them. Require a fresh-process manifest/scan round trip and validate ordered consumption at both file and inner chunk levels.
3. Implement an Iceberg snapshot reader that pins snapshot/branch, plans only its live Vortex files, and applies or rejects deletes precisely. Keep Hail globals, logical schema, and comparator in the Vail descriptor from the first write.
4. Implement descriptor serialization, hash/identity checks, the snapshot-producer hook or coordinator, commit/retry coupling, retention marking, and a live-file fingerprint. Define the precise comparator with null/NaN/nested-key semantics and reject unsupported key types. Add ordered scan with serial concatenation of certified non-overlapping runs or a proven stable k-way merge; otherwise reject the indexed read and require explicit repair/import.

Validation gates: native VORTEX manifest serialization/parse and fresh-process scan; round-trip nested renamed/reordered fields by ID and logical/extension types; empty and nonempty globals across snapshots; multi-file writes with equal and overlapping key ranges; unordered input and external append; explicit failure on unsupported position/equality deletes, then correct application when supported; compaction; optimistic commit conflict/retry; time travel and branch retention; descriptor loss/corruption; and explain plans proving no ordered-output claim leaks from the stock Vortex DataFusion adapter. Record the expected failure of unextended Iceberg engines to read a VORTEX data file. Independent-engine compatibility requires those engines to implement the extension or an accepted standard; catalog acceptance alone does not establish it.

The required multi-file read contract supersedes the original optional-certificate/full-sort fallback proposal. See [ordered fragment scans](ordered-fragment-scan.md) for concrete index, planning and scheduling interfaces. The current prototype supports zero or one data file and performs no read-time sort; it does not yet implement this multi-file contract.
