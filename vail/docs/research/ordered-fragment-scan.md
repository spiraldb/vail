## Index contract

Every keyed snapshot must atomically reference an immutable interval index. Its header binds table UUID, snapshot ID, schema ID, key field IDs and logical types in order, comparator/version and reference-genome identity, the complete live-file fingerprint, index format/version, and a content hash. The snapshot summary stores the index pointer and checksum alongside the descriptor pointer/checksum; the descriptor stores matching identity and hash. A commit is valid only if these values agree with the actual Iceberg snapshot and its live files. A concurrent commit or overwrite must rebuild/rebase the index rather than reuse stale evidence. Garbage collection retains indexes reachable from snapshots/tags/branches.

Each leaf represents a **whole-file fragment** initially: canonical data-file URI, physical file SHA-256, row count, Iceberg manifest identity (including sequence/partition information needed to resolve the task), and an exact *typed composite-key* interval `[first_key, last_key]` for nonempty files. Both stored endpoints are inclusive because they are observed row keys, not independently computed per-column extrema. The leaf carries a writer certificate that every adjacent pair of rows, including across input batches, was nondecreasing under the bound comparator and that first/last are the actual endpoints. The writer validates this while streaming sorted rows into Vortex, then binds the certificate to the resulting file identity and snapshot. The **primary write profile** requires monotone, non-interior-overlapping file ranges (`previous.last_key <= next.first_key`) so ordinary reads concatenate. Equal-key groups may cross touching boundaries; group-complete operators carry/reconcile the open boundary group downstream. Interior overlap (`previous.last_key > next.first_key`) requires an optional explicit merge profile and is rejected by the primary writer. Zero-row snapshots have no leaves or interval. Future subfile fragments need explicit row-range identities and independent boundary proofs; the PR's byte-to-row split mapping alone is not such a proof.

Encode each component with its logical type, missing marker, direction, and the comparator's exact semantics; compare the **whole tuple lexicographically**. Key nulls, including missing nested components, must use the versioned Hail comparator. A missing key is still an indexed value and may be the last interval endpoint. `NULLS LAST` applies in both directions for the currently established scalar subset; no Unicode, floating-point, genomic, or complex-key certificate should be issued until its comparator has an oracle-backed implementation. Prefix keys are not interchangeable with full tuples. General Iceberg `lower_bounds`/`upper_bounds` are per-column statistics and cannot prove a lexicographic interval or intra-file sortedness. A per-file Iceberg `sort_order_id` is useful metadata, but also does not prove the Vail comparator or cross-file order.

The index is a paged, immutable ordered interval dictionary: leaves sorted by `first_key` (stable tie by file identity), with each internal page recording subtree maximum `last_key` and row/file counts. The maximum endpoint lets an interval query visit earlier-starting fragments that still overlap a requested range, but this simple augmentation alone carries no output-sensitive complexity guarantee for arbitrary overlap. A range query has independently inclusive/exclusive endpoints. Prune `[a,b]` against query `(lo,hi)` only when the **whole-key** intervals are disjoint under those flags: for example `b == lo` is prunable when the query excludes `lo`, while duplicates at an included boundary require retaining the leaf. Index pages are checksummed and loaded lazily; a page's bound can overselect but must never omit a matching fragment. Semantic corruption, unknown comparator, missing index, missing leaf, changed file identity, or an unproven run fails keyed read. Import/repair is a separate explicit operation that sorts or validates source data and commits a new certified snapshot.

## Planning against the PR's APIs

1. Pin an Iceberg snapshot and verify its Vail descriptor/index identities and checksums. Traverse only index pages intersecting the whole-key query interval, yielding candidate leaf identities in `first_key` order. For a full scan, visit leaves in that order. Ordinary column projection must retain hidden full-key columns until scheduling/merge and key-bound checks finish; a later projection can discard them.
2. Resolve selected leaves to actual `FileScanTask`s for the **same** pinned snapshot, validating path, format, full-file start/length, file size, record count, deletes, field IDs/schema and relevant sequence/partition metadata against the certificate. The PR's [`FileScanTask`](https://github.com/apache/iceberg-rust/blob/0252fe9174aa3062da51328c444a765aa7de2dae/crates/iceberg/src/scan/task.rs#L31-L88) has the necessary path/offset/record-count fields and [projected fields, deletes, partition and sort-order accessors](https://github.com/apache/iceberg-rust/blob/0252fe9174aa3062da51328c444a765aa7de2dae/crates/iceberg/src/scan/task.rs#L185-L247). Its [manifest-to-task construction](https://github.com/apache/iceberg-rust/blob/0252fe9174aa3062da51328c444a765aa7de2dae/crates/iceberg/src/scan/context.rs#L139-L173) also attaches delete, sequence and partition context; Vail must not reconstruct only path and offset while dropping those semantics. Validate **the same task objects that will be read**, avoiding a second `plan_files()` call after checks.
3. The present public [`TableScan::plan_files()`](https://github.com/apache/iceberg-rust/blob/0252fe9174aa3062da51328c444a765aa7de2dae/crates/iceberg/src/scan/mod.rs#L385-L405) streams planned tasks from concurrent manifest workers ([manifest file workers](https://github.com/apache/iceberg-rust/blob/0252fe9174aa3062da51328c444a765aa7de2dae/crates/iceberg/src/scan/mod.rs#L424-L430), [entry workers](https://github.com/apache/iceberg-rust/blob/0252fe9174aa3062da51328c444a765aa7de2dae/crates/iceberg/src/scan/mod.rs#L475-L504)). It is **not an interval-index lookup** and does not guarantee task order. A first correctness implementation may enumerate all manifest tasks without reading data files, join selected tasks by identity, and reorder them by index leaf; this is metadata-only pruning of *data reads* but still O(F) manifest planning/time and memory if materialized, where F is all live files. To achieve O(log F + K) index-page lookup and candidate planning for K selected fragments, a later targeted manifest/task-resolution seam is needed (or a validated task record stored in the index with all delete/snapshot dependencies). Do not claim logarithmic total planning with the current PR API. A leaf-to-manifest location pointer can make targeted lookup possible only if Iceberg's manifest and delete association are still validated at that snapshot.
4. Feed verified tasks to the PR's public [`ArrowReader::read(FileScanTaskStream)`](https://github.com/apache/iceberg-rust/blob/0252fe9174aa3062da51328c444a765aa7de2dae/crates/iceberg/src/arrow/reader/pipeline.rs#L58-L102). Its concurrency-1 branch concatenates task input order; its concurrency>1 branch uses `try_buffer_unordered` and `try_flatten_unordered`. Thus disjoint intervals can use concurrency 1 for direct ordered concatenation, or a Vail scheduler may prefetch files concurrently but must buffer/emit by index ordinal. Do not call [`TableScan::to_arrow()`](https://github.com/apache/iceberg-rust/blob/0252fe9174aa3062da51328c444a765aa7de2dae/crates/iceberg/src/scan/mod.rs#L507-L522) after resolving/validating tasks: it calls `plan_files()` again and loses the verified ordering. The Vortex reader's own [scan builder and array stream](https://github.com/apache/iceberg-rust/blob/0252fe9174aa3062da51328c444a765aa7de2dae/crates/iceberg/src/arrow/reader/vortex.rs#L205-L227) preserve physical row sequence under the pinned Vortex default.

## Scheduling and merge rule

For each candidate run, `first_key <= last_key` under the bound comparator. If the previous run's `last_key <` the next run's `first_key`, direct concatenation is globally ordered with a strict range gap. Equality also permits **nondecreasing** concatenation in the primary profile, but a duplicate-key group may cross the run boundary: a group/join operator must carry an open group or reconcile the boundary rather than treat the partitions as independently group-complete. If `last_key > next.first_key`, the intervals have interior overlap and concatenation is wrong even though each file is sorted.

For overlap, use a bounded streaming k-way merge of individually ordered PR reader streams, comparing row keys with the exact same versioned comparator as the index. Open every indexed run that might precede the next emitted key: before emitting active minimum key `k`, activate unopened candidate runs whose `first_key <= k`, then recompute the minimum. Index endpoints are conservative when filters/deletes remove boundary rows, so early opening is safe. A deterministic file ordinal/row ordinal tie-breaker is needed only where observable equal-key order is part of the contract; otherwise preserve all duplicate rows without inventing uniqueness. Cap concurrently active runs and per-run batch buffers; if overlap fan-in exceeds the configured profile, reject or require a write-time compaction/repair. A disjoint run after an overlap component can resume ordered concatenation. DataFusion's `SortPreservingMergeExec` may implement the merge only when its physical key comparator is proved identical; the existing prototype's `SortExec` is a write/repair tool, not an ordinary read step.

For the primary **monotone endpoint** profile (`previous.last <= next.first`), a paged search tree can select K candidate intervals in O(log F + K) metadata-index work (plus page-fetch granularity), including every equal-boundary leaf, with O(page size + output-buffer metadata) memory and no data-file I/O for pruned intervals. For the optional interior-overlap profile, the simple subtree-max augmentation costs O(pages visited + K); a stronger O(log F + K) output-sensitive claim requires a separately proved interval-tree design and adversarial tests. The **current** PR task resolver adds O(F) manifest work as above regardless of index lookup. For N rows processed in selected fragments, ordered-concatenation reads decode O(N) data in index order; overlapping reads decode O(N) and perform O(N log W) key comparisons with W active runs, plus bounded prefetch and batch memory proportional to W. A current read-side SHA-256 check also reads all B bytes of each selected whole file before decoding, so a narrow range query still pays O(B_selected) verification I/O; avoiding that later requires a trusted immutable object identity or authenticated subfile chunks. Predicates/deletes may discard rows but cannot turn a sorted stream into an unsorted one. These bounds exclude network/codec cost and cannot promise a fixed memory cap when unbounded W is allowed.

## Adversarial gates

* Two individually sorted files created in reverse name/manifest order with disjoint key intervals; delay the first file's I/O. Output must follow interval order regardless of task completion.
* Two files with equal boundary keys; all duplicates survive, and a group-by-key sees one complete group. Then test overlapping distinct values and verify the streaming merge emits globally nondecreasing keys without a full sort.
* A compound mixed-direction key with missing first and trailing components, inclusive/exclusive range endpoints, and one leaf starting below the query but ending inside it. Index pruning must retain exactly the possible matches; never derive the tuple range from separate column min/max.
* Corrupt/missing index, wrong comparator version, changed file checksum or snapshot ID, missing task, extra manifest file, delete file, and an imported unsorted file all fail keyed read. Explicit repair may create a new certified snapshot, but normal read does not repair.
* Stress many disjoint leaves to measure index-page residency and manifest-planning cost separately; stress a long overlap chain to hit the configured fan-in cap. The latter must produce a bounded rejection or valid streaming result, not silently materialize and sort the table.
