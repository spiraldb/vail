## What order the APIs deliver

* **Within one Vortex file/task:** The PR's [Vortex reader](https://github.com/apache/iceberg-rust/blob/0252fe9174aa3062da51328c444a765aa7de2dae/crates/iceberg/src/arrow/reader/vortex.rs#L205-L227) creates `vortex_file.scan()` with projection, filter, row range, optional split size and positional deletes, then calls `into_array_stream()`. It does not override `ordered`. At Vortex 0.86.1, [`VortexFile::scan()`](https://github.com/vortex-data/vortex/blob/d1fe2dc46d2b947a2304122d0d0423332fcb77a3/vortex-file/src/file.rs#L215-L221) constructs `ScanBuilder`, whose [`ordered` default is `true`](https://github.com/vortex-data/vortex/blob/d1fe2dc46d2b947a2304122d0d0423332fcb77a3/vortex-layout/src/scan/scan_builder.rs#L89-L105). The scan [uses `buffered` for ordered splits](https://github.com/vortex-data/vortex/blob/d1fe2dc46d2b947a2304122d0d0423332fcb77a3/vortex-layout/src/scan/scan_builder.rs#L444-L459). Thus the single-file reader preserves **physical file row order** through parallel splits; this says nothing about whether keys in the file were sorted. Filtering and deletes remove rows without introducing a key sort. Byte-range scan tasks [map boundaries to disjoint contiguous row ranges](https://github.com/apache/iceberg-rust/blob/0252fe9174aa3062da51328c444a765aa7de2dae/crates/iceberg/src/arrow/reader/vortex.rs#L838-L850), but tasks may be emitted in another order.
* **Writer:** [`VortexWriter::write`](https://github.com/apache/iceberg-rust/blob/0252fe9174aa3062da51328c444a765aa7de2dae/crates/iceberg/src/writer/file_writer/vortex_writer.rs#L438-L501) converts each caller batch and sends it sequentially through a bounded channel; the background write [consumes that stream](https://github.com/apache/iceberg-rust/blob/0252fe9174aa3062da51328c444a765aa7de2dae/crates/iceberg/src/writer/file_writer/vortex_writer.rs#L151-L195). The PR exposes no key-sort setting in `VortexWriterBuilder` and does not sort batches. Its [`DataFileBuilder`](https://github.com/apache/iceberg-rust/blob/0252fe9174aa3062da51328c444a765aa7de2dae/crates/iceberg/src/writer/file_writer/vortex_writer.rs#L278-L295) records format, counts, size and bounds, but no `sort_order_id`; statistics bounds are not an ordering proof. Callers must establish any required physical key order before writing and avoid claiming a sorted Iceberg file merely because source batches arrived in that order unless it is verified.
* **Across files:** [`ArrowReaderBuilder` defaults file concurrency to CPU count](https://github.com/apache/iceberg-rust/blob/0252fe9174aa3062da51328c444a765aa7de2dae/crates/iceberg/src/arrow/reader/mod.rs#L65-L84). With concurrency above one, the [read pipeline](https://github.com/apache/iceberg-rust/blob/0252fe9174aa3062da51328c444a765aa7de2dae/crates/iceberg/src/arrow/reader/pipeline.rs#L77-L101) uses `try_buffer_unordered` and `try_flatten_unordered`, interleaving batches as tasks finish. Setting `with_data_file_concurrency_limit(1)` concatenates tasks in their input order, but [`TableScan::plan_files`](https://github.com/apache/iceberg-rust/blob/0252fe9174aa3062da51328c444a765aa7de2dae/crates/iceberg/src/scan/mod.rs#L424-L430) and [manifest-entry processing](https://github.com/apache/iceberg-rust/blob/0252fe9174aa3062da51328c444a765aa7de2dae/crates/iceberg/src/scan/mod.rs#L475-L504) are concurrent, and neither sorts tasks by key. Even a deterministic file listing would not guarantee a global key order for overlapping ranges. The PR [propagates `sort_order_id`/resolved sort order into scan tasks](https://github.com/apache/iceberg-rust/blob/0252fe9174aa3062da51328c444a765aa7de2dae/crates/iceberg/src/scan/context.rs#L100-L124), but this is file metadata, not a merge or validation of global order. Its [DataFusion scan advertises empty `EquivalenceProperties`](https://github.com/apache/iceberg-rust/blob/0252fe9174aa3062da51328c444a765aa7de2dae/crates/integrations/datafusion/src/physical_plan/scan.rs#L106-L116), which correctly avoids asserting output ordering.

## Bounded Vail integration

For the current bounded **zero-or-one-file** Vail storage API, use the PR's Vortex writer for nonempty data, read via the PR's Arrow reader with `with_data_file_concurrency_limit(1)`, and assert the input row sequence survives a write/read roundtrip. The single-file Vortex scan default supports that preservation claim; an empty snapshot has no row-order claim. Keep `ordered_runs = None` unless a sorted-run proof has actually been persisted and validated. This roundtrip is not a keyed or globally sorted table-read API. A future keyed multi-file read must use a snapshot-bound typed composite-key interval index to select and schedule verified fragments in interval order. The primary write profile should create monotone ranges (`previous.last <= next.first`) that ordinary reads concatenate; touching equal-key boundaries require downstream group reconciliation. An optional explicit interior-overlap profile can use a sorted *streaming* merge under a fan-in bound. It must never silently sort an entire table on read; missing or invalid index/proof requires rejection or an explicit repair operation outside read. Neither reader concurrency `1`, Iceberg sort-order metadata, file min/max bounds, nor the single-file `ordered` scan default substitutes for the index. The design is detailed in [ordered-fragment-scan.md](ordered-fragment-scan.md). This does not claim full Hail comparator parity for Unicode strings, floating point or genomic keys.

Minimal checks for the current slice: (1) write deliberately descending values in multiple batches to one Vortex file, then assert identical physical row sequence on Arrow read and `ordered_runs = None`; (2) read one file across many batches and row splits, including a filter and positional delete, and assert retained rows stay in physical order. Future keyed multifile tests: write two individually sorted files with disjoint, touching-equal, and overlapping key intervals; vary file completion timing and verify that the index dictates scheduling, all duplicates survive, and overlap uses streaming merge. An imported file with no certified interval must fail keyed read. Restrict comparator assertions to the currently supported integer/Boolean/ASCII key subset.
