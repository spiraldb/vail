# DataFusion ordering audit for Vail

Inspected `apache/datafusion` at commit `23f6f94c308a800748a5f8b7a5b85d5e41e5dc95` (workspace version 55.1.0). Source references below are paths relative to that checkout with one-based line numbers. This is a source audit, not an execution test. The checkout's `AGENTS.md` applies to upstream edits; none were made.

## Decision

Use DataFusion's physical ordering and distribution properties as a **local** proof, then keep Vail's own proof of *global* and *range* order at API boundaries. A Hail Table with a declared key must not infer globally sorted collection from `output_ordering()` alone. `required_input_ordering()` explicitly means ordering **within each partition**, and `output_ordering()` carries the same meaning (`datafusion/physical-plan/src/execution_plan.rs:212-223,1211-1218`). `PlanProperties` stores ordering derived from `EquivalenceProperties` beside a separate `Partitioning`; it has no single global-order bit (`datafusion/physical-plan/src/execution_plan.rs:1490-1524`).

Represent Vail ordering as a conservative proof: `Unordered`, `Local(keys)`, `RangePartitioned(keys, split_points, partition_ids)`, `OrderedRuns(keys, bounds, run_ids)`, `RangeOrdered(keys, bounds, partition_ids)`, or `Global(keys)`. `OrderedRuns` means locally sorted streams whose ranges may overlap. `RangeOrdered` additionally requires partition traversal order and a proof that each stream's maximum is no greater than the next stream's minimum under the same comparator; equal boundaries are allowed for row sortedness. Strictly disjoint bounds or explicit key ownership are a stronger proof needed by algorithms that process a complete equal-key group inside one partition. If the ranges overlap in distinct values, use a sorted merge, not concatenation. The source or exchange must really route rows according to its certified bounds. A one-partition `Local` can become `Global`. A multi-partition `Local` needs a sorted merge; verified `RangeOrdered` may be concatenated in partition order. Ordinary collection cannot establish global order. Keep key uniqueness and stable tie order as separate facts: lexicographic sortedness does not prove either.

## Existing facilities and exact limits

| `Partitioning` / distribution | `RoundRobinBatch`, `Hash`, `Range`, `UnknownPartitioning` (`datafusion/physical-expr/src/partitioning.rs:122-132`). `Distribution` offers unspecified, single, and key partitioned; no ordered distribution (`datafusion/physical-expr/src/partitioning.rs:755-769`). `RangePartitioning` stores lexicographic keys and split points, but its contract is trusted from the source (`datafusion/physical-expr/src/partitioning.rs:154-169,205-249`). Sorting each range on a *different* key does not establish a global order on that key. |
| `SortPreservingMergeExec` | Requires locally sorted child partitions, produces one partition and advertises the merged ordering (`datafusion/physical-plan/src/sorts/sort_preserving_merge.rs:91-119,160-185,261-280`). Add a unique row tie-breaker when Hail-compatible deterministic order requires one; even input-stream-stable ties need stable upstream order. |
| `RepartitionExec` | `Range` routing exists (`datafusion/physical-plan/src/repartition/mod.rs:566-582,1063-1095,2273-2281`) despite a stale blanket warning that range optimizer/execution is unimplemented (`datafusion/physical-expr/src/partitioning.rs:201-203`). Never equate range-routed with locally sorted. Hash/round-robin exchange usually invalidates a keyed traversal proof. |
| `CoalescePartitionsExec` and collection | Coalesce makes one partition but states no output order and clears ordering metadata (`datafusion/physical-plan/src/coalesce_partitions.rs:50-52,86-110`). `collect()` calls `execute_stream`; with two or more partitions that inserts `CoalescePartitionsExec` (`datafusion/physical-plan/src/execution_plan.rs:1778-1814`). `collect_partitioned()` retains partition vectors by index after asynchronous execution (`datafusion/physical-plan/src/execution_plan.rs:1817-1859`), but it does not sort rows or validate ranges. | Never call plain `collect()` on a multi-partition keyed plan expecting keyed row order. | Limits and TopK | `GlobalLimitExec` requires one input partition, retains input equivalences and says it maintains input order (`datafusion/physical-plan/src/limit.rs:95-103,157-166`). `LocalLimitExec` takes a limit in every input partition, retaining partitioning/order (`datafusion/physical-plan/src/limit.rs:370-401,450-452`). `SortExec` and sorted merge can have `fetch` (`datafusion/physical-plan/src/sorts/sort.rs:1115`; `datafusion/physical-plan/src/sorts/sort_preserving_merge.rs:122-125`). | A global `head(n)` needs an ordered single stream if the Hail call implies key order. Local limit is not a global head. Test equal sort keys and skip/fetch, since nondeterministic ties can select different rows. |
| Windows / joins | Window operators require local partition/order by keys and require a single partition when no `partition_by` exists (`datafusion/physical-plan/src/windows/window_agg_exec.rs:233-263`; `datafusion/physical-plan/src/windows/bounded_window_agg_exec.rs:437-464`). Explicitly downgrade proof after joins unless a narrowly reviewed rule proves it. |
| File scans | FileScanConfig exposes file groups, `preserve_order`, declared `output_ordering`, and optional output partitioning (`datafusion/datasource/src/file_scan_config/mod.rs:175-199,849-899`). It validates ordering only *within each group*, including the order of file ranges, and expects an upstream sorted merge for multiple groups (`datafusion/datasource/src/file_scan_config/mod.rs:1278-1306`). Ordered scans constrain work stealing (`datafusion/datasource/src/file_scan_config/mod.rs:175-180`). File-group repartitioning has a preserve-order path (`datafusion/datasource/src/file_groups.rs:269-283`). | A Vortex/Iceberg-backed scan adapter must furnish truthful local ordering, range bounds, and scan scheduling. Do not infer global ordering from file names, Iceberg sort-order declaration, or a Vortex ordered scan hint without checking emitted partitions. |

The integrated physical optimizer merges locally sorted partitions with `SortPreservingMergeExec` when enforcing a single partition, otherwise it coalesces (`datafusion/physical-optimizer/src/ensure_requirements/enforce_distribution.rs:817-840`). It recognizes matching range schemes in co-partitioned children only when the range descriptors match (`datafusion/physical-optimizer/src/ensure_requirements/enforce_distribution.rs:1270-1286`). It can also adapt a source range scheme to a peer's key expressions (`datafusion/physical-expr/src/partitioning.rs:565-594`). This is useful for joins; it is not a global ordered Table contract. Optimizer repartitioning and sort elimination must be followed by Vail's final proof check against the *optimized physical plan*.

## Correctness traps and minimal adversarial tests

1. **Local versus global:** two sorted partitions, `[2,4]` and `[1,3]`. Assert both advertise local `k ASC`; plain `collect()` must not be accepted as globally ordered, while `SortPreservingMergeExec(k)` yields `[1,2,3,4]`. Vary batch sizes and completion timing to expose coalesce interleaving.
2. **Range is not local sort:** route `[3,1,2,6,4,5]` into ranges `<4` and `>=4`; assert range membership, but reject a global-order proof until each partition is sorted. Repeat with `DESC`, null first/last, compound keys, split-point equality, empty ranges, and split-point type coercion. This targets `RangePartitioning` and `RangeRouter` (`datafusion/physical-expr/src/partitioning.rs:154-169`; `datafusion/physical-plan/src/repartition/mod.rs:566-582`).
3. **Local sort of wrong key:** begin with correct `RangeOrdered(k)` and sort each partition on `v`; reject `Global(v)` and downgrade to `RangePartitioned(k)` with `Local(v)`. `SortExec::with_preserve_partitioning(true)` is the trigger.
4. **Exchange and source scheduling:** put hash and round-robin repartitions over sorted partitions; verify the optimizer's final physical properties and Vail proof downgrade. For scans, use file groups with interleaved and overlapping min/max ranges, and work stealing enabled; accept local order only when `validated_output_ordering` and scheduler behavior support it (`datafusion/datasource/src/file_scan_config/mod.rs:1295-1306`).
5. **TopK / ties:** two partitions with repeated key `7`, distinct row IDs, and `LIMIT 2`; compare local limits, unordered coalesce, sorted merge with both tie policies, and unique `(key,row_id)` ordering. Assert membership and deterministic order only for the total key.
6. **Join and window boundary:** a no-partition window must get single-partition input; a partitioned window should preserve only its local key. Exercise inner/left/right/full sort-merge and hash joins with one-to-many matches, null join keys, and build-side final output. Vail must reject stale global/range proofs after a key or partitioning change.

These should be small `MemTable`/custom `ExecutionPlan` fixtures that assert both resulting row sequences and `output_partitioning`/`output_ordering` on the optimized plan. Add deliberately unverified source declarations to confirm the Vail proof layer refuses to promote them; DataFusion trusts source declarations and will not validate them at runtime. A validated source manifest still needs its own checks.

## Bounded Sol implementation package: ordering proof spike

1. Create a small Vail Rust crate pinned to an agreed dependency set. Define `OrderProof` and an analyzer over `Arc<dyn ExecutionPlan>` at the result boundary. The analyzer starts conservative, recognizes verified scan manifests, local sort, `SortPreservingMergeExec`, range routing, one-partition plans, and explicitly downgrades coalesce/repartition/joins whose semantics are not proved. Require exact expression, `SortOptions`, schema index, partition count, and split-point match. Preserve provenance so a failure explains the first invalidating node.
2. Add one verified in-memory source fixture with two partitions and an optional range manifest. Implement `collect_keyed` that validates the optimized plan and inserts `SortPreservingMergeExec` when all partitions have a common local key; otherwise return a clear error (or request an explicit sort in the caller). Prototype range-concatenation separately only after runtime or manifest validation of local sortedness and disjoint bounds.
3. Run the first five tests above and one join/window downgrade test. Success criterion: no unordered multi-partition path returns a `Global` proof; sorted merge returns exact expected rows; adversarial source metadata fails closed. Stop before Vortex/Iceberg scan implementation, Python API, optimizer rewrites, or distributed execution.

## Review of the current Vail plan and DataFusion 55.0.0 candidate

The current `vail/docs/PLAN.md` correctly separates local and global order (lines 70-81), calls for sorted merge at ordered consumers (104-106), and flags the Arrow 60 versus 59.2 dependency break (159-165). Two wording corrections are needed before implementing its rules:

1. `PLAN.md:92` says a join should restore required output key order when the physical join destroys it. That is the ordinary keyed rule, **with a Hail exception**: Hail's `TableJoin` source explicitly warns that a prefix join can return out-of-order result keys when the left has duplicate full keys and the right has distinct full keys sharing the join prefix (`hail/hail/hail/src/is/hail/expr/ir/TableIR.scala:2206-2215`). Preserve that observable exception where it occurs; do not silently sort every such join merely because the result declares a key. Mark its physical order unknown and make later operations handle that fact. `PLAN.md:95`'s “effective order” therefore means the actual guaranteed order after operation-specific exceptions, not every declared key. The Hail inventory already records this caveat (`vail/docs/research/hail-table-contract.md:21`).
2. `PLAN.md:76,106` correctly allows equal-key boundary overlap in its general model. For an ordered concatenation, `max(left) == min(right)` still yields sorted rows but can split an equal-key group across partitions; a per-partition group, prefix join, scan summary, or limit with stronger tie semantics may need a boundary merge or explicit group ownership. Strictly disjoint certified ranges are one safe fast path. Overlap in *distinct* key values needs a sorted merge. DataFusion `RangePartitioning` uses strict split points and a single partition per key according to its boundary convention (`datafusion/physical-expr/src/partitioning.rs:154-183`); it does not express Vail's general overlapping run bounds. Keep that richer fact in Vail metadata.

The exact DataFusion `55.0.0` tag is local at commit `d5552342012888b7d1a3ab88d92e3d292fc0cde0`. Its `Cargo.toml:81-92` declares Arrow 59.2.0, as the plan says. It already contains `Partitioning::Range` and `RangePartitioning::try_new` (`55.0.0:datafusion/physical-expr/src/partitioning.rs:121-128,204-235`), plus range batch routing in `RepartitionExec` (`55.0.0:datafusion/physical-plan/src/repartition/mod.rs:1001-1060`). The tag still says global `SortExec` needs `SinglePartition` and has a TODO for ordered distribution/range sort (`55.0.0:datafusion/physical-plan/src/sorts/sort.rs:1269-1275`). Compared with inspected HEAD, the tag lacks `RangePartitioning::adapt`, schema-aware `RangeRouter` construction/`RangeExpr::try_new_with_schema`, and the HEAD's range-aware co-partitioned relationship handling (`datafusion/physical-expr/src/partitioning.rs:565-594`; `datafusion/physical-plan/src/repartition/mod.rs:566-582,700-719`; `datafusion/physical-optimizer/src/ensure_requirements/enforce_distribution.rs:1150-1229,1270-1286`). Its optimizer enforces unsatisfied co-partitioned children with hash repartition (`55.0.0:datafusion/physical-optimizer/src/ensure_requirements/enforce_distribution.rs:1050-1108`). Thus 55.0.0 is a plausible Arrow-compatible proof-spike target, but implementation must not assume the HEAD-only range optimizer APIs. Exact `=55.0.0` or revision pins for all coupled DataFusion crates and a `cargo tree -d`/compile gate remain necessary; Vortex's plain `version = "55.0.0"` is a semver requirement, not an exact pin.
